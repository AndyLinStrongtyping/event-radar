# 展館雷達：文化攻略與主題館的搜尋內容計畫

**規劃日期：2026-10-25。這是編輯與工程待辦，不代表下列攻略已發布、關鍵字有確定搜尋量，或網站已被 Google 收錄。** 優先讓訪客能查清楚「能不能去、看什麼、怎麼預約」，再觀察自然搜尋；不以文章數量或廣告分潤作第一階段成果。

## 現有基準與先決條件

- 現站已有故宮北院、南院、奇美、澎湖化石館、左鎮化石園區等**靜態 HTML 館所介紹**，以及獨立的[深海探勘](https://event-radar-preview.onrender.com/explore/ocean/)與[化石探勘](https://event-radar-preview.onrender.com/explore/fossils/)互動頁。介紹頁有館方連結、開放時間與資料核對日期，但尚未逐頁整理完整的票務／預約決策表。
- 2026-10-19～10-24 的 GA4 連結 Search Console 報表顯示 **0 曝光、0 點擊、沒有查詢列**；尚未從 Search Console 原站重新核對，不能據此推估關鍵字需求或宣稱長期沒有搜尋流量。見[每週成效紀錄](weekly-product-review.md)。
- Render 是目前的標準網址；GitHub Pages 快速入口設 `noindex` 並指向 Render。Render 免費服務休眠會影響爬取可用性；發布更多文章前，先用 Search Console「網址審查」查看 Google 實際讀到的 HTML、索引狀態與標準網址。新主題頁內容由 React 顯示，重要搜尋文字若在初始 HTML 缺席，要評估預先產生內容。不要只因 sitemap 有網址就當成已收錄。
- 站內尚未收錄鐵道、海科館與坪林茶博館的完整館所攻略；它們先列為候選，待官方來源、維護能力和真實需求確認後才開頁。

第一波只做兩條內容主線：**文化館行前攻略**（故宮、奇美）與**主題館探索**（化石、海洋）。鐵道、海科館、茶博館是第二波候選。長尾詞可讓頁面更貼近具體問題，但「競爭較低、停留較久、權威度提高、能賺分潤」都只是待量測假設，不能當成已達成結果。Google 建議優先提供原創、可靠、對人有用的內容，而非大量為搜尋引擎製作相似頁面。[依據：Google Search Central](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)

## 首批四頁的內容規格

1. **故宮北院**：開頭先答「今天能不能去、看哪類展、票怎麼選」；分清一般票、資格優惠、需出示的證件和北／南院差異；附館方當期展入口及本站展覽篩選。文物段落只說觀賞線索，旁邊放「展件可能輪替」和官方核對入口。[票種官方來源](https://www.npm.gov.tw/Articles.aspx?l=1&sno=02007004)。
2. **奇美**：一張表分常設展、特展、導覽三種不同費用／預約流程；四大展廳各給一個觀察問題；指出導覽名額和費用須另核對，不把人工補入的《埃及之王：法老》說成完整自動收錄。[參觀指南](https://www.chimeimuseum.org/visit)、[導覽說明](https://www.chimeimuseum.org/visit/60b8a81e414b4/654c95258100b)。
3. **左鎮**：五館建議順序、常設展與活動區分、交通／最後入館時間、化石圖鑑的照片來源與標本可能輪替；導回官方[園區首頁](https://fossil.tnc.gov.tw/)及票務頁。若沒有親身到訪，不寫「實測玩多久」或「小孩最喜歡」。
4. **澎湖化石館**：先釐清週二開館衝突，否則把不確定性放在頁首。潘氏澎湖鱷以科普線索及已授權照片介紹，不保證當日展示位置；把「布氏鯨骨骼不是化石」維持清楚說明。

每頁固定有：一句直接回答、館別與地址、常設／限期展區分、可核對的開館與票務、官方預約入口、`最後核對日期`、來源清單、照片作者與授權，以及「出發前再次確認」連結。可加簡短作者／整理方式說明，避免把資料整理誤寫成到訪體驗。第一階段不做餐廳推薦；若後續實際走訪，再以到訪日期、花費、交通與照片做獨立補充。

**標題示例**（正式發布前依頁面實際內容調整）：

- `故宮北院參觀攻略｜門票資格、當期展覽與文物路線｜展館雷達`
- `奇美博物館常設展怎麼逛？門票、導覽與四大展廳｜展館雷達`
- `左鎮化石園區參觀指南｜五館路線、門票與開放資訊｜展館雷達`

標題與 H1 要準確描述頁面；Google 可能自行改寫搜尋結果標題，沒有「塞入指定字詞就一定顯示」的保證。[依據：Google 標題連結指南](https://developers.google.com/search/docs/appearance/title-link)

## 網站結構與搜尋技術待辦

1. **先審查既有網址**：用 Search Console 網址審查逐一看首頁、故宮北院、奇美、左鎮、深海、化石的 HTTP 200、允許索引、Google 選用的標準網址、已擷取及已轉譯畫面。記錄失敗原因；若 Render 休眠造成爬取不穩，先解決可用性與標準網址承載位置，再擴張內容。
2. **讓重要內容在 HTML 可讀**：現有館所介紹已輸出實際文字，可先優化。深海、化石由 React 顯示，至少測 Google 已轉譯 HTML 是否取得主要段落；若沒有，再評估預先產生主文、保留互動功能。Google 能處理部分 JavaScript，但仍建議伺服器輸出或預先產生，以改善速度與其他爬蟲支援。[依據：Google JavaScript SEO](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)
3. **一頁一個清楚入口**：首頁 → 文化攻略／化石／海洋；館所頁 → 對應主題頁與特展篩選；主題頁 → 館所頁。使用描述性文字連結，不只依賴按鈕或程式跳轉。sitemap 只放希望索引的標準網址；Pages／Render 的重複版本保持一致策略。[依據：Google 連結與網站地圖指南](https://developers.google.com/search/docs/crawling-indexing/links-crawlable)、[sitemap 指南](https://developers.google.com/search/docs/crawling-indexing/sitemaps/overview)
4. **補每頁標題、描述和導覽層級**：每頁唯一 `<title>`、自然語言描述、單一主標題，必要時可補與畫面一致的麵包屑結構化資料。展覽若將來有獨立且可索引的詳情頁，再審查 Event 結構化資料；不要把只有歷史日期的節目或一般館所介紹標成未來活動。結構化資料不保證特殊搜尋呈現。[依據：Google 麵包屑](https://developers.google.com/search/docs/appearance/structured-data/breadcrumb)、[Event](https://developers.google.com/search/docs/appearance/structured-data/event)
   現有奇美館所頁的描述文字出現「博物館博物館」重複，首批編輯時一併修正；其他館所的泛用標題也要依實際新增內容再調整，避免標題承諾頁內沒有的票務表。
5. **資料新鮮度有退出機制**：票價、預約、節日開館和活動期限要保存官方 URL、核對日、下次核對日與狀態；過期或官方頁不可驗證時降級為「請看官網」，不留肯定句。更新日期只在內容確實重新核對或實質修改後才更新。

## 關鍵字判斷與成效驗收

第一週建立表格，每個需求群記：候選查詢、主要 URL、搜尋意圖、官方來源、資訊變動頻率、目前內容缺口、Search Console 實際曝光／點擊、Google Trends 相對趨勢與人工搜尋結果觀察。**沒有數據就填「待測」，不捏造每月搜尋量或難度分數。**先用「訪客是否急著作決定」「來源是否可信」「現有內容能否補強」「維護成本」四項各 1～5 分排優先；有 Search Console 數據後再調整。GA4 的測試流量與朋友分享流量需分開看。

發布後每週看 Search Console 的**網頁 × 查詢**曝光、點擊、點閱率與索引原因，GA4 看自然搜尋進站頁及實際搜尋／前往官方頁事件。新頁至少觀察數週再決定改標題或擴內容；早期 0 曝光先查索引和主站可用性，不立刻認定關鍵字錯了。sitemap 與重新檢索要求可協助發現網址，卻不保證收錄或排名。[依據：Google Search Console](https://developers.google.com/search/docs/monitor-debug/search-console-start)、[重新檢索說明](https://developers.google.com/search/docs/crawling-indexing/ask-google-to-recrawl)
