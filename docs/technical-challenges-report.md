# Event Radar｜技術難點與解決決策報告

核對日：2026-10-18。範圍是目前公開技術預覽與本機已驗證的程式；實際運作紀錄以 [STATUS](../STATUS.md) 及 [技術決策](technical-decisions.md) 為準。本文把「已實作」、「單次驗證」和「尚待觀察」分開，不把設計圖上的未來功能當成現況。

## 一、專案要解決的工程問題

Event Radar 不只是把博物館網頁抓下來。真正的問題是：不同館方提供的資料格式、日期語意與完整度各異；同一活動會重複出現，也可能改期、換地點或從清單暫時消失。若直接顯示原始資料，訪客可能看到過期或無法核對的展覽。

目前的資料路徑如下：

```text
官方 JSON／HTML → 各館 Adapter → 驗證與待審分流
             → 標準化資料 → 交易式匯入／去重／異動紀錄
             → PostgreSQL → Node.js 查詢 API → React 網站
```

排程與來源工作負責啟動匯入；它們不能代替驗證、交易與來源健康檢查。表演場次、海生館當日節目另有自己的時間模型與查詢端點。

## 二、技術難點與處理方式

| 技術難點 | 會造成的錯誤 | 已採取的決策與實作 | 驗證證據及界線 |
| --- | --- | --- | --- |
| **多來源格式不一致** | JSON／HTML 欄位直接滲透到資料庫和前端；某館改版牽動整站 | 每館有 Adapter；限期展進共同模型前驗證館別、標題、真實起訖日與可核對的官方 HTTPS 來源；藝術家、策展人等由美術展擴充表保存。見 [標準化程式](../src/normalize.ts)、[來源盤點](sources.md)、[領域模型](domain-model.md)。 | 單元與隔離資料庫測試涵蓋解析、日期及欄位；Adapter 仍須隨館方改版維護。奇美內部端點是候選來源，尚非穩定自動來源。 |
| **缺日期及不確定資料** | 把「即日起」猜成精確展期，或把沒寫票價當免費 | 保存原始來源紀錄；可確認的限期展才進公開搜尋，缺漏或矛盾者進 `source_records` 待審，附原因供人工核對。沒有結束日不自動判成常設展。見 [匯入流程](../src/ingest.ts)及 [待審作業](operations.md)。 | `source_records`、待審筆數與覆核流程可查；人工覆核仍需館方證據，資料不會因「有紀錄」就自動變正確。 |
| **冪等、去重與異動容易混淆** | 每週重跑多一筆；活動改期卻被當成新活動；不同來源同展重複顯示 | 用穩定來源 ID／官方詳情連結作身分鍵，資料庫以 `(museum_id, source_key)` 唯一約束保護；來源別名存 `exhibition_sources`。內容 hash 用於版本辨識，逐欄比較後把舊／新值寫入 `exhibition_changes`。同館寫入用交易與 advisory lock 抵抗併發。見 [匯入程式](../src/ingest.ts)、[唯一約束](../db/001_init.sql)、[異動表](../db/002_sources_and_changes.sql)。 | 隔離資料庫測試驗證新增、重跑未變與改欄位；保守去重無法保證所有跨來源同名活動都能自動合併，模糊情況寧可待查。 |
| **官方清單突然縮水或換鍵** | 來源只回 2 筆，系統誤認原本 30 筆中的 28 筆取消 | 比較來源筆數與身分鍵；可疑批次記為 `deferred_partial`／`SOURCE_ANOMALY`，暫緩舊資料的缺席判定。有效新資料仍可匯入；正常成功批次的缺席也先做候選，人工核對後才調整基準。見 [限期展匯入](../src/ingest.ts)、[缺席候選表](../db/009_source_missing_candidates.sql)、[技術決策 ER-65／66／73](technical-decisions.md)。 | 合成縮水、換鍵與覆核案例有整合測試；來源真實異常仍要人工判讀，閘門不會自行判斷「網站改版」或「真的停展」。 |
| **不同領域的時間語意** | 把一齣戲的多場次或海生館今天的餵食時間硬塞成單一展期，導致錯誤的未來資訊 | 限期展用日期範圍；表演用 `domain_events`＋`event_sessions`；海洋節目用 `recurring_schedules` 和有 `observed_on` 的成功快照。第 025 migration 以複合外鍵防止場次掛錯領域；OpenAPI 用分型回應。見 [領域模型](domain-model.md)、[資料庫約束](../db/025_domain_child_integrity.sql)、[OpenAPI](openapi.yaml)。 | 表演／海洋整合與契約測試通過；海生館當日表不保證明日適用，特殊日開館只在有官方日期證據時核對。 |
| **排程、失敗重試與重複工作** | 一館逾時拖累整批；worker 中途當掉或重試造成重複匯入 | PostgreSQL `FETCH_SOURCE` 工作使用同來源同日冪等鍵、`FOR UPDATE SKIP LOCKED`、三分鐘租約、有限重試、`dead` 保留及人工 replay；各來源工作獨立，抓取端有 timeout。見 [工作實作](../src/source-jobs.ts)、[每週工作](../.github/workflows/weekly-sync.yml)。 | 2026-10-17 五館特展與歌劇院共六個工作手動 Actions 成功；第一次真正週二排程預定 2026-10-20，尚無跨週證據。Queue 只有抓取工作，歌劇院走獨立命令，並非解析、異動、通知的多階段架構。 |
| **查詢正確性與索引取捨** | 日期範圍查錯、狀態與免費篩選誤導訪客；過早聲稱索引加速 | `GET /exhibitions` 用參數化 SQL、臺灣日期、區間交集、城市／館所／狀態／明確免費條件及分頁。資料庫有身分與日期索引。見 [API](../src/server.ts)、[索引](../db/001_init.sql)。 | HTTP 整合與 OpenAPI 回應驗證涵蓋查詢；關鍵字目前是 `ILIKE`，雖有 title GIN 索引，不能宣稱已用 PostgreSQL 全文搜尋或有量測過的效能提升。 |
| **部署與資料庫版本漂移** | 本機能跑、線上 migration 失敗；CI 綠燈卻無法復原資料 | React 與 Node API 同源部署於 Render，Neon 保存 PostgreSQL；migration 有帳本與 checksum 檢查，部署後用 `/health` 和唯讀 smoke test。資料庫變更前先備份，並在隔離空白庫試還原。見 [部署設定](../render.yaml)、[Migration](../src/migrate.ts)、[備份紀錄](stage-2026-10-18-neon-backup-drill.md)。 | 2026-10-18 正式 Neon 以相容的 PostgreSQL 18.6 工具備份，隔離還原後 25 份 migration、11 館、30 筆展覽、18 筆匯入紀錄筆數相符；只有單次本機演練，尚無加密異地備份與定期輪替。 |
| **資料新鮮度與真實使用證據** | 網站回 200 卻展示久未核對的資料；把自己的測試造訪當成流量成果 | 保留每來源最後成功時間、失敗與待審狀態；官方同步成功才更新 `last_official_success_at`。GA4 量直接造訪，Search Console 量 Google 搜尋；兩者用途分開。見 [來源狀態](../src/server.ts)、[決策 ER-89／90](technical-decisions.md)。 | GA4 即時報表收到測試 `page_view=2`、`session_start=1`；Search Console 處理 15 個固定頁面的 sitemap，但截至核對日沒有可宣稱的自然搜尋或外部使用者數。 |

## 三、三個最適合面試說明的真實案例

### 案例 A：故宮北院在本機可讀，GitHub runner 卻逾時

- **現象**：同一官方 JSON，本機請求成功，GitHub Actions runner 連線出現 `UND_ERR_CONNECT_TIMEOUT`；Render 首次建置也曾抓取失敗。
- **診斷**：先分辨「抓取失敗」與「資料解析失敗」。證據只能證明雲端環境連線逾時，不能推定館方封鎖或故宮沒有展覽。
- **決策**：北院設獨立開關，暫停雲端自動工作；其他六個工作照常執行。本機可透過同一 Adapter 人工同步至 Neon，失敗工作與最後成功時間照實留存。
- **結果與限制**：2026-10-18 本機重新取得 22 筆來源資料，1 筆公開展覽未變、15 筆待審、6 筆略過；這不證明雲端來源已修好。詳見 [ER-91／93](technical-decisions.md)和 [Actions #4](https://github.com/AndyLinStrongtyping/event-radar/actions/runs/39033250246)。

### 案例 B：奇美網頁有內部 JSON，卻不能直接宣稱「已接官方 API」

- **現象**：官網展覽與活動頁使用未公開文件化的 JSON 端點；不同類別 schema 不一致，無 session 呼叫曾回 419，日期可能是區間、多日、即日起或純時間。
- **決策**：以候選 Adapter 隔離奇美欄位、保留原始日期並分類；人工刷新快照和候選表可供核對，但不把候選活動自動發布成正式展覽，也不稱該端點為「官方公開 API」。
- **原因**：能請求一次不等於可長期穩定同步；如果登入狀態、HTML、欄位或篩選行為變化，直接入庫會製造錯誤日期與漏展。
- **待完成**：核對頁面筆數、分頁與 filter 行為、無瀏覽器 session 情況，以及跨多日 schema 穩定，再決定是否升級為正式自動來源。詳見 [奇美來源評估](chimei-internal-endpoint.md)。

### 案例 C：備份工具主版本不相容，CI 通過仍不代表正式庫可復原

- **現象**：CI 的 PostgreSQL 17 合成資料備份／還原成功，但 Neon 實際是 PostgreSQL 18.6；本機 17.11 `pg_dump` 對 18.6 伺服器因版本不相容而失敗。
- **決策**：改用 18.6 相容工具，密碼放在子程序環境變數，備份置於非 OneDrive 本機目錄，產生大小與 SHA-256；只准還原到明確命名的隔離空白庫，執行後比對 migration 和核心表筆數。
- **結果與限制**：成功建立 146,102 bytes 的正式庫快照並單次隔離還原；仍只有一份未加密本機副本，未達異地容災標準。詳見 [備份演練](stage-2026-10-18-neon-backup-drill.md)。

## 四、工程選擇的核心邏輯

1. **正確性先於資料量**：缺日期、來源不明或清單異常時保留待審；不為了讓搜尋結果變多而猜資料。
2. **身分與內容分開**：source key 回答「同一活動嗎」，content hash 和欄位 diff 回答「內容變了嗎」。
3. **資料庫保證最後一道邊界**：程式先查、Adapter 驗證都必要，但唯一約束、交易及外鍵才能擋住併發與錯領域寫入。
4. **來源工作隔離**：一館抓取失敗應留下可追查結果，不抹除舊資料，也不停止其他館。
5. **模型尊重時間語意**：限期展、表演場次、當日觀察表分開，避免一張全是 nullable 欄位的表誤導 API 使用者。
6. **驗證範圍照實呈現**：單元、隔離資料庫、手動線上工作、真實週排程和長期維運是不同層級的證據。

## 五、現況與下一步

目前可準確稱為**公開技術預覽**：Render／Neon 已上線，React 搜尋、Node API、PostgreSQL、來源驗證、異動記錄、部分來源工作與 CI 已有實作及證據。仍需觀察 2026-10-20 首次真正週排程、跨週來源穩定、北院雲端連線、奇美候選來源、異地備份及外部流量。沒有訂閱通知、Email／LINE 推送、AWS 或多階段 production Queue。

面試時可用這段話概括：

> 我做 Event Radar 時最大的挑戰不是抓網頁，而是讓多館資料在重跑、改期和來源故障下仍可信。我用 Adapter 與日期／網址驗證統一資料，靠穩定來源鍵和 PostgreSQL 約束保證冪等，再用欄位異動歷史追蹤改期。對缺漏與異常清單採待審和暫緩缺席判定；不同活動則保留各自的時間模型。公開預覽與部分來源工作已驗證，但週排程跨週穩定和完整災難復原仍在進行。
