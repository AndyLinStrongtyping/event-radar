## 已確認的問題

### P1：不存在的靜態檔案可能使公開服務程序退出

位置：src/server.ts:155–164、407–413。

前端資源路徑先 writeHead(200)，才等待 readFile。不存在的 /react-assets/missing.js 也符合路徑規則；讀檔失敗後進入外層 catch，再以 json() 呼叫 writeHead(500)，會拋出 ERR_HTTP_HEADERS_SENT。非同步請求處理函式沒有再接住這次錯誤，預設 Node 啟動設定可能因此退出。部署後舊分頁仍請求前一版檔名，也可能觸發。

本機以 Node ServerResponse 直接重現二次 writeHead 的 ERR_HTTP_HEADERS_SENT；沒有向正式站送出破壞性測試。修正應先成功讀檔再送標頭，檔案不存在回 404，並確保錯誤回應本身不會再次拋錯。回歸測試需確認不存在的檔案回應後，下一次健康檢查仍正常。

### P1：國美館單筆詳情連線失敗會隱藏既有展覽

位置：src/sources/ntmofa.ts:104–124、src/ingest.ts:234–246、325–327。

詳情取得失敗與資料內容確實無效都被歸入 review。匯入流程遇到 review 就將既有主要來源展覽 visible=false。清單完整度保護只有大量縮水才阻擋，無法保護零星逾時。

本機用三筆清單、一筆詳情逾時重現：accepted=2、review=1、isSuspiciousDrop(3,2)=false。因此已有同來源展覽時，這筆會進入隱藏 SQL 路徑。沒有對正式資料庫執行這個情境。

應區分「暫時無法取得」與「成功取得但驗證不合格」。前者保留上次可用資料、記錄本次失敗並安排重試；不能只因來源暫時失聯就下架。

### P1：人工核對失效後，重複匯入會把場次恢復為正常

位置：src/domain-events.ts:157–160、211–230。

先人工核對延期或取消，之後來源內容變更但仍回 scheduled，第一次匯入會設 unknown 並清除 manual 標記。第二次匯入完全相同的來源資料，仍執行場次 UPSERT；因 status_origin 已是 source，落入 ELSE EXCLUDED.status，又改成 scheduled。

更嚴重的是第二次內容雜湊相同，計數為 unchanged，不進入異動紀錄分支，因此可能在沒有新證據與狀態異動紀錄下恢復公開正常場次。既有整合測試只驗第一次變更後為 unknown，隨即人工覆核，沒有測中間再匯入一次。

這項由 SQL 狀態轉換確認，尚未在獨立 PostgreSQL 重跑。應保存「須重新核對」狀態及其來源版本；重複匯入同版本不能清除，直到有新的明確證據或人工核對。

### P2：公開服務沒有接住閒置資料庫連線的錯誤事件

位置：src/server.ts:10。

連線池只建立而未註冊 error 事件。已安裝的 pg-pool 在閒置連線斷線時會 pool.emit('error', err, client)；這不是請求內 await pool.query() 的拒絕，外層請求 catch 接不到。資料庫重啟或網路中斷可能導致 Node 未處理的 error 事件並退出。

應註冊連線池錯誤處理，記錄不含憑證的訊息，交由連線池移除失效連線；健康檢查反映實際可用性。需加獨立測試驗證斷線後程序仍在、連線可恢復。未中斷正式 Neon 進行實測。

### P2：科博館網路錯誤不會進入既有重試流程

位置：src/nmns-api.ts:15、src/retry-policy.ts:4。

科博館請求逾時或網路錯誤統一改成「科博館 API 連線失敗」，但重試分類只辨識「來源連線失敗」或英文網路錯誤。原錯誤已被移除，所以會被當成不可重試。

本機直接呼叫分類函式已確認回 false。應使用結構化錯誤種類或可重試旗標，不靠中文訊息比對；同時保留不得記錄含 API Key 網址的保護。
