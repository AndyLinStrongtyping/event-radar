# Event Radar 技術處理與決策紀錄

最後對照程式：2026-10-15（臺灣時間）。本文件是「**現在怎麼處理、為什麼這樣選、證據在哪裡、下一步的條件**」的單一入口；功能是否已完成仍以[統一進度](../STATUS.md)為準。狀態分成 **已實作／本機驗證**、**已設計但未啟用**、**尚未實作**。有 workflow 檔案或架構圖，不等於線上服務正在執行。

## 產品與系統邊界

### ER-01｜產品範圍：臺灣博物館的限期展覽（已實作／本機驗證）

- **處理**：搜尋資料以特展、期間限定展為主；九館的常設展、館所背景與開館資訊放在另外的介紹頁。一般音樂會、市集、講座不自動混入特展 API。
- **決策**：先把「有明確展期、可追到館方原頁」的資料做可靠。不同活動類型的日期、票務與地點語意不同，混在同一模型會讓搜尋結果失真。
- **證據／界線**：[需求](requirements.md)、[架構](architecture.md)、[九館導覽](../web/guides/)。導覽頁存在不表示該館已有特展匯入器。

### ER-02｜Node.js + TypeScript 後端（已實作／本機驗證）

- **處理**：Node.js 執行匯入、同步、查詢 API 與本機管理工具；TypeScript 做型別檢查，執行時用 Node 的 type stripping。主要進入點在 [`src/`](../src/) 與 [`package.json`](../package.json)。
- **決策**：沿用已熟悉的 JavaScript／Node.js 生態；來源 adapter 與 API 共用正規化型別，不先引入大型框架。型別檢查協助開發，但外部 JSON 仍必須在執行時驗證。
- **界線**：不是微服務；目前是一個本機應用與數個命令列工作。

### ER-03｜React + Vite 互動首頁（已實作／本機驗證）

- **處理**：[`frontend/src/main.tsx`](../frontend/src/main.tsx)用 React 管理搜尋條件、城市／館所連動、展覽卡、詳情展開、票務切換與分頁；Vite 建置後由同一 Node 服務提供。九館介紹仍是獨立靜態頁。
- **決策**：互動狀態已超過單純靜態頁的舒適範圍，所以只把首頁轉 React，不重寫資料庫與已有導覽。載入時的「發掘文物」動畫是介面回饋，不是資料同步動畫；遵守減少動態效果設定。
- **證據／界線**：[React 階段紀錄](stage-2026-10-10-react.md)。本機介面已驗證，尚未公開部署。

## 資料來源與清洗

### ER-04｜每館獨立 source adapter（已實作／本機驗證）

- **處理**：來源分成科博館 API／公開 JSON、故宮南院官方頁、故宮北院 JSON、海生館 JSON、科工館 JSON 加官方頁核對；各自解析後交給共同正規化函式。程式在 [`src/sources/`](../src/sources/) 與 [`src/ingest.ts`](../src/ingest.ts)。
- **決策**：館方欄位、日期格式與展館識別不同，先在 adapter 隔離差異，避免把館別特例散進搜尋 API。來源格式變更時能明確定位是哪一家館。
- **界線**：這五館可本機執行來源工作；臺博館、臺史博、科教館等有導覽但沒有展覽 adapter。

### ER-05｜科博館私人 Key 與公開資料備援（已實作／本機驗證）

- **處理**：有 `NMNS_API_KEY` 時，使用科博館 OpenAPI 的 `Exhibition/list` 和 `Calendar/weekHours`；沒有 Key 時，展覽可退回已設定的官方公開 JSON，逐日開放時間則回「請查官網」。請求只發到館方 HTTPS；錯誤訊息不輸出含 Key 的 URL。見 [`src/nmns-api.ts`](../src/nmns-api.ts)、[`src/visit-status.ts`](../src/visit-status.ts)。
- **決策**：金鑰用伺服端環境變數，絕不放前端或 Git。API 金鑰解決存取，**不代表已有 Queue**；備援只用於有相同資料語意的展覽，不假裝公開 JSON 也有逐日行事曆。
- **證據／界線**：[科博館實測階段紀錄](stage-2026-10-05-phase4.md)。線上 Secret 尚未設定、線上每日同步尚未啟用。

### ER-06｜故宮南院的 HTML 擷取（已實作／本機驗證）

- **處理**：讀當期與預告兩個官方列表，只解析特定展覽卡與完整起訖日期；民國年換西元，同一官方詳情網址合併。列表結構消失、同展資訊衝突或沒有可匯入的限期展，整批報錯。見 [`src/sources/npm-south.ts`](../src/sources/npm-south.ts)。
- **決策**：館方無已確認可用的公開展覽 API 時，用範圍明確的官方頁；對 HTML 變動採「停止、待核對」，不默默抓到導航或常設展。
- **界線**：這是官方網頁同步，不是館方 API；目前只取列表第一頁所定義的當期／預告入口，完整涵蓋率須持續核對。

### ER-07｜故宮北院與海生館公開 JSON（已實作／本機驗證）

- **處理**：故宮 JSON 先辨識北／南院，再驗完整展期、排除已結束及疑似長期展；海生館支援已觀察到的民國七碼、西元八碼及 ISO 日期，並檢查真實日曆。無效或缺漏資料留在 `source_records` 待審，不進公開搜尋。見 [`npm-north.ts`](../src/sources/npm-north.ts)、[`nmmba.ts`](../src/sources/nmmba.ts)。
- **決策**：公部門開放資料的日期與分類不完全一致；寧可少展示，也不猜結束日或把另一院區的展覽放錯館。
- **界線**：缺結束日**不自動判為常設展**；單筆待審不等於整批成功上架。

### ER-08｜科工館雙來源交叉驗證（已實作／本機驗證）

- **處理**：公開 JSON 的特展候選，必須在官方特展列表找到**唯一且同展名、同展期**的詳情頁才公開；不符的來源紀錄待審。見 [`src/sources/nstm.ts`](../src/sources/nstm.ts)。
- **決策**：單靠 JSON 沒有可靠的逐筆官方詳情網址；交叉驗證後才讓使用者能回到館方查證。
- **證據／界線**：[科工館階段紀錄](stage-2026-10-05-phase3.md)記錄本機資料與隔離結果。館方 HTML 版型變更可能使整批停止，需要人檢查。

### ER-09｜奇美人工資料、文化部補充與只讀監測（部分實作／本機驗證）

- **處理**：現有一筆人工核對的奇美展覽。文化部 iCulture JSON 只作補充：按奇美主辦單位和官方逐筆頁過濾，同展相鄰場次合併後，再對照奇美頁的展名與完整展期；不符者待審。`check:chimei` 比對初始 HTML 可見連結，也核對已知特展詳情，**不寫資料庫**。見 [`moc-chimei.ts`](../src/sources/moc-chimei.ts)、[`check-chimei.ts`](../src/check-chimei.ts)。
- **決策**：奇美[特展列表](https://www.chimeimuseum.org/exhibition-event)與[最新消息](https://www.chimeimuseum.org/news)的初始 HTML 不是完整動態列表；文化部資料的分頁與涵蓋率也未證明完整。不能把「抓到一筆」包裝為全館同步。
- **證據／界線**：[奇美監測階段紀錄](stage-2026-10-10-chimei-monitor.md)。正式完整列表、新聞與臨時休館自動同步仍未完成。

### ER-10｜共同正規化與網址安全檢查（已實作／本機驗證）

- **處理**：[`src/normalize.ts`](../src/normalize.ts)檢查館別、必填展名、官方 HTTPS 網域、有效起訖日期與欄位長度，產生統一 `ExhibitionDraft`、來源鍵及內容 SHA-256。假資料明確標記 `isSample`。
- **決策**：adapter 只處理來源差異；同一入口實施跨來源的最低品質門檻，防止錯館、假官網與不可能的日期。SHA-256 用於比較正規化內容，不是授權或真實性證明。
- **界線**：有通過格式驗證，仍不代表來源已涵蓋全館，也不代表票價即時正確。

### ER-11｜原始資料、隔離與人工補正（已實作／本機驗證）

- **處理**：來源原始 JSON、來源鍵、網址、狀態及原因進 `source_records`；有效展覽才進 `exhibitions`。海生館與故宮北院可透過本機 CLI 或只綁 `127.0.0.1`、密碼保護的審核頁，留下補正日期、證據網址、審查者與備註；下次匯入相同來源 hash 時套用。來源變動時撤回舊補正與可見性。見 [`review-service.ts`](../src/review-service.ts)、[`corrections.ts`](../src/corrections.ts)、[`admin-server.ts`](../src/admin-server.ts)。
- **決策**：資料不完整時保留可追溯的原始證據，人工修正也要有版本邊界，不能靠無痕手動改公開資料。
- **界線**：補正目前只支援兩個來源；審核仍需人眼判斷，沒有自動寄送待審通知。

## 資料庫、同步與可靠性

### ER-12｜PostgreSQL 資料模型（已實作／本機驗證）

- **處理**：[`db/`](../db/)有 `museums`、`exhibitions`、`ingestion_runs`、`exhibition_sources`、`exhibition_changes`、`source_records`、`review_corrections`、`sync_attempts`。外鍵、唯一鍵、日期檢查和索引承擔底線約束；migration 由 [`src/migrate.ts`](../src/migrate.ts)執行。
- **決策**：展覽主表負責查詢；來源別名負責同一展的多來源關係；原始紀錄與待審分開；匯入及重試紀錄分開。關聯式資料庫適合這些一致性與追溯需求，現階段無須另加搜尋服務。
- **界線**：Docker Compose 目前只啟動本機 PostgreSQL，**沒有整站容器映像或線上資料庫**。

### ER-13｜整批驗證、交易與匯入品質閘門（已實作／本機驗證）

- **處理**：[`src/ingest.ts`](../src/ingest.ts)先取得、解析來源，再在 PostgreSQL 交易中套用補正、來源紀錄、展覽、別名與異動。解析或寫入錯誤會 rollback，`ingestion_runs` 記失敗；來源 0 筆也記失敗。若有來源紀錄、但套用補正後 **0 筆可公開展覽**，只提交原始／待審紀錄與失敗統計，程序回傳非零碼；不更新成功時間，也不新增展覽。同一來源鍵原已公開、這次轉為 `review` 時，按來源別名或先前記錄的官方網址找出展覽；如果它仍以該來源為主來源，就在交易內設為不可見。其他有效來源重新匯入時可接手主來源並恢復可見。來源格式消失、重複來源鍵或歧義去重同樣不當成成功。
- **決策**：單筆有問題時保留待審證據；整批無法公開時不能用「程序處理完畢」冒充同步成功，否則來源健康狀態會掩蓋資料品質下降。這類品質失敗屬確定性問題，不安排暫時性網路重試；人工補正後可重跑。
- **界線／驗證**：批次有有效展覽也有待審紀錄時可以成功，但失去有效依據的既有主展覽會下架；其他來源已接手的展覽不受舊來源待審影響。隔離 PostgreSQL 整合測試覆蓋空陣列、全待審、有效轉待審、混合批次、備援來源接手、來源變動使舊補正失效及補正後恢復公開；見 [`test/ingest.integration.cjs`](../test/ingest.integration.cjs)。**來源紀錄從清單消失**只記缺席候選，不會自動下架（見 ER-30），須另定館方下架語意。目前採保守規則：即使來源合法地暫無限期展，只要 0 筆可公開資料也標為需人工核對，日後有館方證據才針對該來源放寬。

### ER-14｜冪等鍵、去重與來源別名（已實作／本機驗證）

- **處理**：同來源用穩定來源鍵與唯一約束 upsert；同館跨來源先比對官方詳情網址，網址不同時只在正規化展名、展廳相同且展期重疊時合併。來源對同一展覽的關係存 `exhibition_sources`；候選超過一筆就停下待判。見 [`src/dedupe.ts`](../src/dedupe.ts)、[`src/ingest.ts`](../src/ingest.ts)。
- **決策**：每天重跑不能新增重複展覽，但也不能把名稱相似的不同展硬併。**同館**是合併邊界，跨館巡迴展目前保持分開。
- **界線**：不是通用模糊比對引擎；沒有跨館同展關聯。

### ER-15｜欄位異動紀錄（已實作／本機驗證）

- **處理**：新資料與主展覽比對 `title`、`venue`、`startDate`、`endDate`、`priceNote`、`sourceUrl`、`summary`，在同一匯入交易中寫 `exhibition_changes` 的舊值、新值與時間；API 可查最近 100 筆。見 [`src/dedupe.ts`](../src/dedupe.ts)、[`src/server.ts`](../src/server.ts)。
- **決策**：日期、地點等變更比單純覆蓋更值得追蹤，亦提供日後通知的可信事件基礎。
- **界線**：目前只記錄異動，**沒有訂閱者通知、異動事件 Queue 或任意版本重播**；本機來源工作 Queue 不承載這些事件。

### ER-16｜同館匯入併發控制（已實作／本機驗證）

- **處理**：匯入交易使用 PostgreSQL `pg_advisory_xact_lock(hashtext(museum))`；人工補正也對館別取得同類交易鎖。唯一約束再做資料層保護。
- **決策**：同一館兩個匯入／補正流程若同時寫入，先序列化同館操作；不同館仍可獨立處理。
- **界線**：這是資料庫交易鎖，**不是** Queue worker 的併發控制或分散式排程器。

### ER-17｜來源別重試與手動重跑（已實作／本機驗證）

- **處理**：[`src/sync-source.ts`](../src/sync-source.ts)以子程序跑單館匯入，90 秒逾時；只對連線錯誤、429、5xx 等暫時性錯誤重試，最多三次，間隔 30 秒、2 分鐘；每次嘗試寫 `sync_attempts`。`sync:failed` 只重跑最近失敗的來源。見 [`retry-policy.ts`](../src/retry-policy.ts)。
- **決策**：一館來源故障不拖垮其他館；格式錯誤不是暫時性故障，不應無限制重抓。這條直接同步流程現在供本機手動操作；未啟用的每日 workflow 已於 2026-10-11 改用來源 Queue，見 ER-33 與 ER-39。
- **界線**：直接 `sync` 不經過 Queue；本機手動工作表有 `dead` 狀態與人工重播，但沒有線上 worker pool 或自動 replay。

### ER-18｜每日排程與奇美每週檢查（已設計但未啟用）

- **處理**：當時的每日 workflow 定義五館獨立 job；該檔現已更名為[每週 workflow](../.github/workflows/weekly-sync.yml)。[奇美檢查](../.github/workflows/chimei-check.yml)定義每週只讀檢查。兩者都受 `EVENT_RADAR_SYNC_ENABLED` 變數閘門控制。
- **決策**：目標是約每日一次，符合特展更新節奏；先有可手動執行、可觀察的工作，再開啟無人值守排程。奇美來源尚不完整，不納入五館每日資料庫同步。
- **界線**：尚無遠端 PostgreSQL／Secret 與已啟用的線上排程；workflow 檔存在不等於每天有新資料。

### ER-19｜來源新鮮度與故障呈現（已實作／本機驗證）

- **處理**：[`db/008_official_sync_freshness.sql`](../db/008_official_sync_freshness.sql)加入 `last_official_success_at`。`last_success_at` 留作成功匯入時間；只有 `--official` 成功取得並匯入有效資料才刷新官方同步時間，`--file`／`--snapshot` 不會刷新。舊資料只從已記錄成功的 `sync_attempts` 回填可證明的官方時間，來源不明的舊匯入不推定為官方同步。`/museums` 以官方時間加最近同步嘗試回傳 `recent`、`failed`、`stale`、`manual` 等狀態；最近失敗優先顯示。見 [`source-freshness.ts`](../src/source-freshness.ts) 與 [`sync-status.ts`](../src/sync-status.ts)。
- **決策**：展覽可能幾個月不改，但**是否重新取得官方來源**需要獨立觀測；七天是官方同步健康提醒門檻，不是展覽有效期限。手動處理一份舊快照不能把過期來源顯示為近期同步。
- **界線／驗證**：頁面和本機命令列仍是被動狀態，沒有主動告警或儀表板。無可信歷史同步紀錄的舊資料需等下次成功官方同步後才能顯示近期狀態；整合測試覆蓋「舊官方時間＋成功嘗試＋剛匯入手動快照」仍顯示過期。

## 查詢 API 與使用者資訊

### ER-20｜REST 查詢契約與搜尋條件（已實作／本機驗證）

- **處理**：[`src/server.ts`](../src/server.ts)提供 `/health`、`/museums`、`/exhibitions`、單展詳情、異動紀錄與 `/visit-status`。可按城市、館所、關鍵字、日期交集、狀態與明確免費條件查詢；關鍵字中的 `%`、`_`、`#` 先跳脫，按字面而非 SQL 萬用字元搜尋。限制分頁大小，錯誤有固定 JSON 格式。見 [API 契約](api.md)。
- **決策**：前端只做呈現與條件選取，篩選、日期語意及模擬資料隱藏在 API 一處決定；沒有公開寫入 API。
- **界線**：`status` 是依查詢基準日計算，不是存在 DB 裡會過期的旗標。

### ER-21｜搜尋索引的取捨（已量測；暫不新增）

- **處理**：現有 `(end_date,start_date,id)` B-tree 及標題全文 GIN；關鍵字實際使用 `ILIKE '%詞%'`，因此現有全文 GIN **不會服務這個查詢**。先前以約 28 筆本機資料做 `EXPLAIN (ANALYZE, BUFFERS)`，小表順序掃描約 0.03–0.47 ms。見[第五階段索引紀錄](stage-2026-10-05-phase5.md)。
- **決策**：目前增加複合索引只增加寫入與維護成本。資料量及查詢延遲上升時，先重測，再比較 `pg_trgm` 或有條件的館別／展期索引。
- **界線**：不能宣稱已實作高效全文搜尋；現階段是資料量小、查詢足夠快。

### ER-22｜票價、購票與免費判定（已實作；人工維護）

- **處理**：九館一般票務資料與已確認的奇美法老展票價放在 [`src/ticketing.ts`](../src/ticketing.ts)，保留官方資訊頁、購票入口及人工核對日期。API 把「個別特展票」和「一般入館票」分欄。`admission=free` 只接受來源明確寫「免費／免費入場／免門票」，不從空白或一般館票推論。見[票務來源](ticketing.md)。
- **決策**：特展票可能另購且價格常變；錯誤的「免費」會直接誤導行程。寧可顯示未知並連回官方，也不填猜測票價。
- **界線**：這不是售票庫存或即時票價同步；`checkedOn` 是人工核對日。

### ER-23｜開館與臨時休館（部分實作）

- **處理**：九館介紹頁整理平常開放時間、例行休館日與館方連結。科博館有 Key 且查詢在未來一週內時，用官方行事曆回開／休館；其餘未核對日期回 `unknown`。奇美週三可能有特別場次，因此不單憑星期判定當日休館。見 [`visit-status.ts`](../src/visit-status.ts)、[開館來源](opening-hours.md)。
- **決策**：特展展期不等於館所當天開門；國定假日、颱風、活動場次可臨時調整。沒有可靠逐日官方資料就引導使用者出發前查館方。
- **界線**：除科博館指定日期外，沒有九館的即時逐日休館同步；奇美新聞頁尚未自動解析臨時公告。

### ER-24｜博物館介紹、照片與交通（已實作；靜態／外部服務）

- **處理**：九頁介紹常設展特色、平常開館時間及官方查證入口；照片有替代文字及來源說明。交通可由使用者選起點，開啟地圖的大眾運輸或開車路線。見 [`web/guides/`](../web/guides/) 與[圖片來源](sources.md)。
- **決策**：常設展資訊變動慢、需要人工挑選亮點；交通由專門地圖服務計算，避免本站以縣市中心假裝算出「最佳路線」。使用者輸入的起點不存到本站資料庫。
- **界線**：導覽不是即時展件目錄；本站不計算車程、票價或路線排名。

## 驗證、運行與尚未採用的技術

### ER-25｜單元、資料庫整合與 CI（已實作／本機及 GitHub 驗證）

- **處理**：Node 內建 test runner 檢查 adapter、日期、去重、變更、重試、來源狀態與票務；隔離 PostgreSQL 整合測試真正啟動 API，檢查回應欄位、型別、錯誤碼、分頁及資料庫匯入。[CI workflow](../.github/workflows/ci.yml)在 push／PR 跑 TypeScript、單元及整合測試。
- **決策**：CI 是「何時自動跑驗證」的流程，測試框架是「怎麼寫驗證」的工具；目前用 Node 內建 runner，**不需要為了 CI 另外裝 Jest**。外部館方即時資料會變，CI 用固定樣本檢查契約，不把官方當天內容寫死。
- **證據／界線**：目前本機 `npm test` 33/33、`npm run typecheck` 與隔離 PostgreSQL `npm run test:integration` 通過；外部館方當天資料不固定，CI 不把即時回應內容寫死。這不等於線上每日同步已運作。

### ER-26｜Docker、設定與資料庫（已實作於本機）

- **處理**：[`compose.yaml`](../compose.yaml)提供綁在 `127.0.0.1` 的 PostgreSQL 17、健康檢查與持久化 volume；Node 程式於主機執行。`.env` 存本機 Key 與連線資訊，受 Git 忽略；線上 workflow 只預留 Secret 名稱。
- **決策**：本機需要可重現的資料庫，但目前沒有部署網站的要求，所以沒有為 Node/React 建整站 Docker image。
- **界線**：「有 Docker」目前指本機 DB，不代表網站已容器化或上雲。

### ER-27｜本機管理介面與資料安全（已實作；限本機）

- **處理**：公開 API 只有讀取；人工補正介面另外綁定回環位址並要求密碼。外部來源要求 HTTPS 與預期館方網域、請求有逾時／大小上限；SQL 查詢使用參數。模擬資料預設不進公開搜尋。
- **決策**：資料來源與管理操作都跨信任邊界；最小化公開寫入面，避免錯誤資料或 Key 被前端、日誌與第三方取得。
- **界線**：本機管理頁不是可直接暴露到公網的完整使用者身分系統；公開部署前仍需重新檢查權限、網路與 Secret。

### ER-28｜持久化 Queue／worker／DLQ（FETCH_SOURCE 本機版已實作）

- **處理**：已用 PostgreSQL `source_jobs` 實作限本機、手動入列的 `FETCH_SOURCE` 工作，詳見 ER-33。`sync_attempts` 仍是嘗試日誌；工作狀態存在獨立資料表。
- **決策**：目前只有五館低頻同步，因此沿用既有 PostgreSQL，不加 Redis/BullMQ 服務。先驗證來源工作可獨立領取、崩潰恢復及死信重播；資料抓取、解析、標準化、變更偵測仍在一次 `ingest --official` 中，未拆成多段事件鏈。
- **界線**：每日 workflow 的程式路徑已於 2026-10-11 接入來源 Queue，但仍未在線上啟動。`exhibition_changes` 是 DB 異動紀錄，**不是**已發送的事件通知。見[後續方向](future-roadmap.md)。

### ER-29｜訂閱通知、遠端觀測、AWS 與公開部署（尚未實作）

- **規劃**：通知前先有訂閱同意、只通知哪些異動、頻率限制與防重寄；本機已能量測部分來源健康指標（ER-32），但遠端監控與主動告警仍待設計。若公開部署，先準備可連線資料庫與 Secret、手動跑五館並核對，再啟用排程與網站。AWS 服務的選擇需以實測需求和費用決定。
- **決策**：先使資料正確且可追溯，才擴大為無人值守的對外服務。架構概念圖中的 SQS、RDS、CloudWatch、Email／LINE、DLQ 與 Replay 都是方向，不是已上線能力。
- **界線**：目前沒有公開 Event Radar 網址、線上每日同步、推播或 AWS 部署；不要在履歷或面試中說成已完成。

### ER-30｜官方清單缺席候選（已實作／本機驗證）

- **處理**：只有 `--official` 取得至少一筆有效展覽且完成交易匯入時，才將本次來源鍵與官方網址和先前公開、未結束、仍由該 provider 主導的展覽相比。這次沒看到的來源別名寫入 [`source_missing_candidates`](../db/009_source_missing_candidates.sql)，記首次／最近缺席時間、連續缺席次數及匯入 run；重新出現在官方資料，或由另一有效 provider 接手時自動結案。`ingestion_runs.missing_count` 記當次候選數；`npm run review -- --missing` 和登入後的本機 `/missing` 頁可查看候選及官方原頁。見 [`source-missing.ts`](../src/source-missing.ts)。
- **決策**：某筆資料不在本次清單，可能是展覽下架，也可能是分頁、來源涵蓋率或暫時性資料缺漏；只產生可追溯的人工核對線索，**不自動改展期或下架**。空來源／全待審批次原本就失敗，不觸發缺席判定；手動檔案及快照也不觸發。
- **界線／證據**：目前沒有館方取消展覽的可靠機器可讀訊號，也沒有主動通知。即使成功官方匯入，來源本身也不一定是完整清單，候選不是「已取消」證明。隔離 PostgreSQL 整合測試涵蓋連續缺席、手動快照不計數、重新出現結案、展覽仍可見，以及本機審核頁；見 [`test/ingest.integration.cjs`](../test/ingest.integration.cjs)。人工核對另見 ER-31。

### ER-31｜缺席候選的人工核對紀錄（已實作／本機驗證）

- **處理**：本機 `review`、`review:approve`、`admin` 命令讀取 Git 忽略的 `.env`；登入本機管理頁後，可在 `/missing/record` 查候選、來源原頁、展期與最近核對歷史，將本次觀測標為「核對後保留展覽」或「需後續追查」，填審查人、證據網址與說明。[`missing-review-service.ts`](../src/missing-review-service.ts)在交易中鎖定仍待審的候選，檢查 HTTPS 證據網址與原始來源相同網域，將核對結果追加到 [`source_missing_reviews`](../db/010_missing_candidate_reviews.sql)，並記住核對時的缺席次數；同一次觀測不接受重複提交。下次官方同步仍缺席時會增加次數，再次標為需核對；來源重新出現後再度缺席則開始新週期。命令列 `review -- --missing` 也顯示 `needsReview` 與最近核對次數。
- **決策**：清單缺席不是取消證據，審查操作只留人工判斷和可追溯紀錄，**不改展覽可見狀態或展期**。即使選「需後續追查」也不自動隱藏；如需根據館方明確公告取消或結束來下架，須另設有證據與可逆操作的流程。每次新缺席都重新待審，避免舊核對長期掩蓋來源變化。
- **界線／證據**：相同網域只限制誤填外站，不能證明館方頁真的寫有相關資訊，仍需人眼查證。本機管理頁不是公網管理系統；沒有 Email／LINE 提醒。隔離 PostgreSQL 整合測試涵蓋登入／CSRF、證據網域、重複提交、再次缺席與重新出現後重開週期。見[本階段紀錄](stage-2026-10-10-missing-review.md)。

### ER-32｜本機來源健康觀測（已實作／本機驗證）

- **處理**：[`source-health-report.ts`](../src/source-health-report.ts)以 `sync_id` 取每次工作的最後一筆 `sync_attempts`，再計算最近七天工作數、最終失敗數、有重試的工作數與最終失敗率；並讀取最後官方成功時間、來源待審量與未核對的新缺席候選。[`source-health.ts`](../src/source-health.ts)沿用七天新鮮度判定，依「最近失敗 → 過期 → 無官方成功 → 無工作證據 → 有待審 → 近期正常」的順序給出單一狀態。`npm run sync:status` 回傳 JSON；登入後的本機 `/health` 頁顯示中文摘要。CLI 現在也會讀取 Git 忽略的 `.env`。
- **決策**：`sync_attempts` 每一次重試都是一列，但使用者關心的是一次來源工作最後是否成功；不能把「先失敗、後成功」算成一次獨立失敗。最近匯入本機快照不等於最近取得官方來源；沒有可靠紀錄時顯示無紀錄。健康狀態只是排查順序，不能證明展覽資料完整或館方今天開門。
- **界線／證據**：七天是同步健康提醒門檻，不是館方資料更新週期或展覽有效期。本機資料的來源狀態目前多數為「尚無官方成功紀錄」，因沒有可證明的近期官方工作；不為了讓儀表板變綠而補造時間。沒有自動告警、遠端儀表板或線上排程。單元測試驗證狀態優先序；隔離 PostgreSQL 整合測試驗證重試後成功只計一次、待審數與登入限制。見[本階段紀錄](stage-2026-10-10-source-health.md)。

### ER-33｜PostgreSQL 來源工作佇列（已實作／本機整合測試）

- **處理**：[`db/011_source_jobs.sql`](../db/011_source_jobs.sql)保存來源工作、每日冪等鍵、狀態、嘗試次數、可領取時間、三分鐘租約、worker token、錯誤與重播來源。手動 `jobs:enqueue` 可對五館建立 `FETCH_SOURCE` 工作；同館同日重送只回傳既有工作。`jobs:work` 以 `FOR UPDATE SKIP LOCKED` 原子領取，到期租約會記失敗並退避後重領；worker 對單館執行既有 `ingest --official`，每次最多 90 秒。暫時錯誤按 30 秒、2 分鐘退避，最多三次；非暫時錯誤或達上限進 `dead`。完成結果以 token／未過期租約保護，並寫入 `sync_attempts`。`jobs:status` 查狀態，`jobs:replay -- --id` 對死信建立新工作，原工作與歷史不刪。見 [`source-jobs.ts`](../src/source-jobs.ts) 與 [`source-job-cli.ts`](../src/source-job-cli.ts)。
- **決策**：佇列只包住單一來源官方匯入，不再呼叫內含重試的 `sync-source.ts`，避免雙層重試。每日排程當時維持原路徑與關閉狀態；2026-10-11 已改接來源 Queue，仍關閉線上執行，見 ER-39。`sync_id` 用 job id，健康報告能按一份工作計最終結果。
- **界線／證據**：這不是 `FETCH → PARSE → CHECK_CHANGE` 多階段 Queue，也沒有通知 worker、遠端調度或自動維運。worker 崩潰後需有下一次 `jobs:work` 才會掃描過期租約；租約過期時舊程序可能仍完成來源寫入，匯入本身依資料庫冪等規則處理，舊 worker 的**工作結果**不會覆蓋新租約。隔離 PostgreSQL 整合測試涵蓋同日去重、並行領取、退避、死信、新工作重播、過期租約與舊 token 拒寫；不宣稱已在真實館方流量下壓測。見[本階段紀錄](stage-2026-10-10-source-queue.md)。

### ER-34｜官方清單縮水時暫緩缺席判定（已實作／本機整合測試）

- **處理**：[`source-coverage.ts`](../src/source-coverage.ts)在每次成功的 `--official` 匯入交易中，按館所與 provider 比較本次不同來源鍵數，以及解析後可公開展覽數。首次官方匯入只在 [`official_source_baselines`](../db/012_source_coverage.sql)建立基準，不推斷舊展缺席。往後若任一筆數由至少 4 筆的基準跌至一半或更少且至少少 2 筆，將 `ingestion_runs.coverage_status` 記為 `deferred_partial`，保留上次基準，整次跳過缺席候選新增及結案；匯入有效展覽仍可成功。未觸發時記 `checked`，才執行既有缺席比對。匯入紀錄保存兩種筆數與比較基準，命令列與本機 `/health` 頁也提示暫緩，`sync:status` JSON 帶最新判定。手動檔案／快照標為 `not_applicable`。
- **決策**：空批次與 0 筆可公開資料已由原匯入品質閘門處理；非空但只回一部分仍會錯誤放大缺席候選。兩種筆數一起比，可偵測來源漏頁及解析器退化。將資料匯入和缺席判斷分開，保留新取得的有效展覽，但不要根據疑似不完整清單提出新的缺席判斷。疑似縮水的批次不覆寫基準，下次恢復完整清單後可繼續比對。
- **界線／證據**：筆數門檻只是啟發式，慢慢縮小、小清單或筆數不變但內容換掉仍可能漏判；真正撤展須核對館方原頁。`deferred_partial` 仍是匯入成功，最後官方成功時間會刷新，不能解讀為清單完整。首次建立基準也可能是部分清單，所以不對舊展做缺席判斷；必要時人工查 `ingestion_runs` 和來源原頁。隔離 PostgreSQL 測試涵蓋首次基準、疑似部分回應不改基準、完整恢復與解析後筆數驟降；單元測試驗證門檻。見[本階段紀錄](stage-2026-10-10-source-coverage.md)。

**2026-10-10 審查後修正 ER-34**：完整度評估現已移到既有展覽可見性變更之前。`deferred_partial` 除了暫緩缺席候選，也暫緩本批待審紀錄造成的舊展隱藏；原始資料仍寫入待審。官方來源 0 筆可公開資料則記失敗、保留待審，不用這批資料隱藏舊展；手動快照仍依已確認的單筆失效規則處理。公開 `/museums` 額外回傳 `coverageStatus`，前端把完整度警示與新鮮度訊息並列。隔離 PostgreSQL 整合測試以科工館 6 筆變為可核對 2 筆的完整匯入流程驗證舊展可見、待審保留、公開 API 狀態與完整恢復。筆數規則仍只是警示，不保證內容完整。

**2026-10-11 小清單修正 ER-34**：國美館目前只有 3 筆可公開限期展，即使 12 張來源卡全在，解析後只剩 1 筆，舊門檻也不會警示。`isSuspiciousDrop` 現對基準 2–3 筆且縮至一半以下也回 `deferred_partial`；隔離 PostgreSQL 測試以 12 張原始卡、3→1 筆公開展驗證仍保留 3 筆可信基準。3→2 不警示；季節換展可能造成誤報，須由站長核對後按 ER-44 接受新基準。這是保護可見性與缺席判定的啟發式，不能證明來源完整。

### ER-35｜跨頁回到 React 搜尋區（已實作／本機瀏覽器驗證）

- **處理**：靜態館所介紹連到 `/?museum=<id>#explore-title`。首頁 React 掛載後再依既有 hash 捲至特展搜尋標題，避免瀏覽器在目標節點尚未渲染時放棄錨點；URL 的館所參數仍由館所 API 載入後設定篩選。
- **決策**：保留可分享的普通連結與原生錨點語意，只補首次 React 載入的捲動時機。
- **界線／證據**：本機桌面瀏覽器從奇美介紹頁實際點擊後，網址帶入 `museum=chimei`、篩選選中奇美，搜尋標題移至視窗頂部附近；尚未測所有手機瀏覽器。

### ER-36｜可重建的資料庫 migration 與舊庫基線（已實作／隔離 PostgreSQL 驗證）

- **處理**：[`src/migrate.ts`](../src/migrate.ts)依檔名順序執行 001–012；每份 SQL 與 `schema_migrations` 的檔名、SHA-256 checksum 一起在同一交易中提交，失敗回滾，重跑跳過已套用版本；內容和已登記 checksum 不同則停止。session advisory lock 阻止兩個遷移程序同時改 schema。新空白庫只要 `npm run migrate`；舊版手動建表庫不會自動重建，需明確執行 `--baseline-existing` 並通過必要表、欄位、索引核對。
- **初始化入口**：[`compose.yaml`](../compose.yaml)只啟動空白 PostgreSQL，不再掛載 `db/` 給容器自動執行；schema 的唯一入口是 `npm run migrate`，避免 Docker 首次建立資料卷時繞過帳本。
- **決策**：SQL 檔保留歷史原貌，runner 移除舊腳本外層的 `BEGIN`／`COMMIT`，才能把腳本與帳本寫入包進同一交易。初始檔的館所列是系統參考資料；正式資料不自動寫入模擬展覽。基線只給已更新至 012 的舊庫使用，不讓不完整資料庫跳過 migration。
- **界線／證據**：結構簽名核對不能證明歷史資料的每一項 backfill 都正確；使用舊庫前仍須備份與人工檢查。隔離 PostgreSQL 整合測試驗證空白庫建置、重跑 0 份、舊庫未授權拒絕與明確基線成功。見[本階段紀錄](stage-2026-10-11-lecture-fixes.md)。

### ER-37｜服務啟動與資料庫就緒（已實作／本機驗證）

- **界線／證據**：單元測試以不可連接的資料庫位址驗證兩個程序不開始監聽；隔離 PostgreSQL 整合測試驗證正常啟動與健康回應。尚無正式部署環境的容器編排 readiness probe。

### ER-39｜每日排程接入單館來源 Queue（已實作／本機驗證）

- **處理**：[`source-job-schedule.ts`](../src/source-job-schedule.ts)以臺灣日期入列一館，使用目標 job ID 領取並等待重試／最終狀態；[`source-jobs.ts`](../src/source-jobs.ts)的選用 ID 篩選同時限制到期租約回收與待辦領取。`jobs:daily` 最多等待八分鐘，成功回零、`dead` 或逾時回非零。[`weekly-sync.yml`](../.github/workflows/weekly-sync.yml)五館工作改呼叫這條路，仍由關閉的變數閘門保護。
- **決策**：五館每日工作彼此獨立，不能因別館先到期而領錯來源；延遲重試須在同一次排程呼叫內等待最終結果，避免第一次可重試失敗就誤判整個工作失敗。同館同日沿用既有冪等鍵，排程重跑不自動重新抓取已成功工作或重播死信。
- **界線／證據**：這不是多階段 Queue，也沒有線上排程運作或主動告警證據。啟用需先備妥可連線資料庫、migration 與 Secrets，再逐館手動驗證。隔離 PostgreSQL 整合測試驗證來源隔離、暫時失敗後成功、同日冪等及永久失敗；型別與單元測試通過。見[階段紀錄](stage-2026-10-11-scheduled-source-queue.md)。

- **排程例外**：來源執行函式意外拋錯時標記為不可重試的 `dead`，避免持續停在 `running`；資料庫記錄結果失敗仍拋出，留待租約回收。隔離 PostgreSQL 測試涵蓋前者。

### ER-40｜奇美官網內部 JSON 端點（候選，尚未接入）

- **觀察**：使用者以 DevTools 發現官網頁面呼叫 `POST /exhibition-event/api`，回應分 `specialEvent`、`permanentEvent`、`expoEvent`，日期格式不固定。本站於 2026-10-11 無 Cookie／CSRF 的 Node POST 收到 419；同日以公開頁正常發出的匿名 session 與 CSRF meta 重送一次，回 200 JSON，三組筆數為 1／4／10。未輸出或保存憑證、回應全文，也沒有嘗試繞過保護。這是**官網內部使用、未公開文件化的 JSON 端點**，不得稱為「奇美官方公開 API」。
- **決策**：先記錄為候選來源，不實作自動 adapter、不加入五館每日 Queue，也不改公開展覽表為可空日期。未來若驗證可持續且可接受的取得方式，只在奇美 adapter 內解析三種不一致的結構：限期特展需完整起訖日才進搜尋；常設展與活動先分開；不明日期留原始值及待審。現有 `normalizeExhibition` 會把奇美來源鍵改為網址，實作 ID 去重前必須改造並測試。欄位歷史與清單縮水判定也需按新來源格式擴充，不能把來源消失當作取消。
- **證據／界線**：[候選來源評估](chimei-internal-endpoint.md)及[2026-10-11 實測](stage-2026-10-11-chimei-probe.md)列出 419／200 兩次路徑、Node.js 只讀 probe、日期／標籤篩選、資料模型差距與完成條件。公開頁前端未見分頁參數、當日唯一特展與詳情頁一致；仍未證明清單無隱含上限、跨日穩定或可持續第三方介接。Probe 故意不匯入、不保存 token 或全文，失敗時不更動舊資料；個人非商業使用也不自動取得內容再利用權利。

### ER-41｜來源同步改為每週候選頻率（已修改程式路徑，未線上啟用）

- **處理**：將原每日同步 workflow 改為[每週二臺灣時間 04:15 的五館排程](../.github/workflows/weekly-sync.yml)，各館仍獨立執行 `jobs:scheduled`；`jobs:daily` 保留為舊命令相容入口。`source-jobs` 的同館同日冪等鍵保持不變，供當天手動重跑及排程重送共用。奇美官網檢查本來就是每週一，候選 JSON 端點仍未加入排程。排程的 `EVENT_RADAR_SYNC_ENABLED` 閘門仍關閉。
- **決策**：特展資訊通常不需要每日重新取得；先以每週一次作為成本與來源負載較低的**預設候選頻率**，重大變動可手動執行單館。公開頁與來源健康狀態改以最後成功取得官方來源的時間判斷，超過 14 天才因時間標示可能過期，容納一個每週週期漏跑。最近七天的工作失敗率是另一個統計窗口，不能混同 14 天門檻。排程頻率與來源可靠性是兩件事：即使每週跑，仍要驗證結果、隔離異常並觀察跨週成功；單次成功不稱穩定來源。
- **界線／證據**：此修改只更動本機程式、設定與說明；沒有啟用 GitHub Actions 線上同步、遠端資料庫或通知。歷史 ER-18／20／32／39 的每日排程或七天新鮮度描述保留為當時決策，由本節取代其**目前設定**。`npm run typecheck`、37 項單元測試、隔離 PostgreSQL 整合測試、前端建置，以及 workflow 靜態核對（每週 cron、五館工作與閘門）均已通過；尚無真正跨週執行證據。

### ER-42｜奇美內部 JSON 的離線候選適配器（已實作，尚未接入匯入）

- **處理**：[`chimei-internal.ts`](../src/sources/chimei-internal.ts)驗證三組頂層陣列，將 `specialEvent` 的 ID、官方特展連結、標題與原始日期轉為共用候選紀錄；只讓單一、有效且完整的起訖日產生 `ExhibitionDraft`。`permanentEvent` 和 `expoEvent` 只計數，不混入限期特展；長期、僅時段、多場次及無法解析的日期保留最小化 `rawDate` 並標待審。來源鍵採 `special:<id>`，[`normalizeExhibition`](../src/normalize.ts)只對符合格式的奇美特展保留此鍵，避免詳情網址變化造成重複。既有只讀 [`probe:chimei`](../src/probe-chimei-source.ts)現在也用適配器回報候選與待審筆數，不保存回應全文或憑證。
- **決策**：先驗證資料模型，再考慮寫入資料庫。奇美官網的單段特展連結可能轉到雙段詳情頁，因此只檢查它是官方 HTTPS 特展路徑；**正式匯入前仍需核對跳轉後詳情、既有人工資料關聯及跨週穩定性**。適配器的 `ready` 僅表示結構可解析，不等於已取得授權、資料完整或能向訪客公開。
- **界線／證據**：42 項單元測試、型別檢查與既有隔離 PostgreSQL 整合測試通過，其中新增測試涵蓋兩種日期寫法、多場次、無效日期、外站網址、單段連結、URL 改變時 ID 穩定、既有人工來源鍵、空回應與重複 ID。2026-10-11 第一次只讀實測收到三組 1／4／10，較嚴格的候選規則將唯一特展列為待審；放寬為有界的字母數字 ID、接受單段官方特展連結後，第二次只讀實測仍為 1／4／10，特展候選 1、待審 0。兩項格式規則同時修改，不能單憑這兩次結果斷定原先是哪一項不符。沒有把內部端點接入 [`ingest.ts`](../src/ingest.ts)、Queue 或每週排程，也沒有聲稱奇美已自動同步。

### ER-43｜官方來源同筆數大幅換項目時暫緩缺席判定（已實作／本機驗證）

- **問題**：原完整度保護只比較來源鍵總數與可公開展覽數。若頁面改版或解析器選到另一塊同樣有六筆資料的區域，總數不變仍可能把原清單全數誤判為缺席。
- **處理**：[`013_source_identity_coverage.sql`](../db/013_source_identity_coverage.sql)為各館／provider 基準增加可空的 `identity_keys`。[`source-coverage.ts`](../src/source-coverage.ts)在原筆數判定之外，比較上次可信清單與本次來源鍵交集；舊基準至少四筆、至少三筆消失且重疊不超過四分之一時，標為 `deferred_partial`，不更新可信基準，暫緩舊展隱藏與缺席候選。有效新展仍可匯入並保存原始待審紀錄。既有只有筆數的基準先保留 `NULL`；下一次未觸發縮水的官方匯入才建立鍵清單，不臆造歷史鍵值。
- **決策**：同筆數換項目也可能是正常季節輪替，因此只要求人工核對，不自動下架、取消或拒絕新展。來源鍵是官方詳情網址或來源 ID 的既有識別值；若館方改用不穩定網址，此規則會偏保守地提醒。`deferred_partial` 仍表示有有效資料成功匯入，與「清單完整」不是同一件事。
- **證據／界線**：43 項單元測試、型別檢查與隔離 PostgreSQL 整合測試通過；整合測試涵蓋 6→6 筆但來源鍵全換、基準不覆寫、缺席候選不新增，以及原有 6→2 筆保護。本機既有資料庫 `npm run migrate` 顯示新套用 1 份、共 13 份。門檻無法證明清單完整；少於四筆、逐次緩慢變化或來源鍵本身不穩定仍需人工看官網。尚未在正式排程跨週觀察。

### ER-44｜官方清單異常後的人工基準更新（已實作／本機驗證）

- **問題**：ER-43 會保留可信基準，避免疑似錯誤清單下架舊展；但館方真的整季換展時，新清單每次仍會被判為 `deferred_partial`，無法恢復正常缺席比對。
- **處理**：[`014_source_baseline_reviews.sql`](../db/014_source_baseline_reviews.sql)讓新官方匯入紀錄保存完整來源鍵快照，並建立不可重複核准同一批次的審查紀錄表。`npm run coverage:baseline -- inspect --source <館別>` 顯示最新官方批次、可信基準與新增／消失的來源鍵；站長對照館方官方頁後，才用 `accept` 提供批次 UUID、同館 HTTPS 證據網址、審查人和理由。[`source-baseline-review.ts`](../src/source-baseline-review.ts)在交易中取得與匯入共用的館別鎖，重新確認它仍是最新成功且被暫緩的官方批次、比較基準未改，然後一次寫入審查與新的可信基準。舊批次或重複核准都拒絕。
- **決策**：核准只表示「以這批清單作為下次比較基準」，**不**表示館方取消舊展，也不更新展覽可見性或將既有缺席候選結案。該批 `ingestion_runs.coverage_status` 保留歷史判定；下一次成功官方同步才重新評估，若清單仍相同便可回 `checked`。歷史批次沒有可靠鍵快照，不做推測回填，也不能用本功能核准。錯誤證據或錯誤人工判斷仍可能讓基準失準，故保留審查紀錄及原始批次供追查；此流程不是自動來源完整性證明。
- **證據／界線**：型別檢查、43 項單元測試與隔離 PostgreSQL 整合測試通過。整合測試涵蓋同筆數全換、預覽差異、錯誤官方網域、非最新批次、重複核准、審查紀錄、核准不隱藏舊展及下次相同清單恢復 `checked`。本機 migration 與實際跨週人工操作狀態見[階段紀錄](stage-2026-10-11-source-baseline-review.md)；沒有在線上啟用同步。

### ER-45｜CI 用 OpenAPI 驗證實際公開 API 回應（已實作／本機驗證）

- **問題**：原整合測試手寫部分欄位斷言；OpenAPI 文件另做靜態檢查。若新增巢狀欄位、改壞 nullable 或 enum，兩者可能各自通過卻互相不符。
- **處理**：[`openapi-response-validator.cjs`](../test/openapi-response-validator.cjs)讀取版本庫內的 [`openapi.yaml`](openapi.yaml)，解析本檔 `$ref`、`allOf`、`nullable`、必填欄位、陣列、型別、enum、數值範圍及已使用的日期／時間／UUID／URI 格式。[隔離 PostgreSQL 整合測試](../test/ingest.integration.cjs)對實際 HTTP 成功與錯誤回應逐層驗證，也要求文件中的每條公開 GET 路由至少有一筆 200 回應受驗；原本的業務斷言仍保留。CI 原已執行此整合測試，因此推送後會自動做相同核對。
- **決策**：針對目前文件實際使用的 schema 功能寫小型驗證器，遇到不支援的組合運算子或 format 明確失敗，不默默略過。這是**測試中的回應契約驗證**，不在正式請求路徑重複解析 schema；也不宣稱是完整的 OpenAPI 3.0 實作。新增 schema 語法或路由時需同步擴充驗證及測試案例。
- **證據／界線**：44 項單元測試、型別檢查及隔離 PostgreSQL 整合測試通過；單元測試刻意注入錯誤 enum 與巢狀購票欄位，確認驗證器會失敗。整合測試涵蓋目前六條 GET 路由的成功回應及既有 400／404 案例。503 與 500 等故障回應仍未以隔離資料庫流程逐條觸發；詳見[階段紀錄](stage-2026-10-11-openapi-response-validation.md)。

### ER-46｜五館真實同步演練與公開待審提示（已實作／本機驗證）

- **觀察**：2026-10-11 臺灣時間逐館執行一次正式來源同步，五館皆成功且無重試。科博館 8 筆、故宮南院 7 筆均無待審；故宮北院 22 筆來源僅 1 筆可公開、15 筆待審、6 筆略過；海生館 30 筆中 4 筆可公開、26 筆待審；科工館 8 筆中 7 筆可公開、1 筆待審。`sync:status` 把後三館列為 `needs_review`，但原公開 `/museums` 只顯示近期取得來源，網站沒有待審量提示；本機 3000 埠另有 2026-10-10 啟動的舊版程序，連新欄位都未提供。
- **處理**：公開 `/museums` 新增按館所計算的 `pendingReviewCount`，只提供數量，不洩露待審原文；React 來源狀態與展覽詳情會提示「可能含歷史資料，未列入搜尋」，待審量大於零時套用提醒樣式。`dataStatus` 原本的時間意義保留，不把「近期取到」誤改為「全部可公開」。OpenAPI 與 API 文件同步更新；隔離資料庫整合測試逐館比對 API 數量與 `source_records`，原有 OpenAPI 回應驗證也會檢查欄位。日常匯入輸出不再列印完整來源鍵清單；鍵仍保存在 `ingestion_runs` 供人工審查。
- **決策／界線**：待審計數包含歷史或長期展，不能解讀為目前漏了幾場特展，也不能自動補日期或核准。五次同日成功只證明這次取得與匯入，**不證明跨週來源穩定或清單完整**。首次可信基準皆為 `baseline_created`，下一次官方同步才會與基準比較。來源錯誤、館方變動及其後的資料品質仍需持續觀測；詳見[階段紀錄](stage-2026-10-11-five-source-drill.md)。

- **決策**：先用公開 JSON 篩出少量候選，避免每次對歷史資料逐頁請求；逐筆頁只是交叉核對，不把來源中任何年份、開幕活動日、出版日或「起」字當完整展期。來源頁改版、標題不完全相同、展期寫法不同時會保守留待審，可能漏收但不猜測。已結束展覽可留作「已結束」查詢，不進當期搜尋；本功能不核實常設展目前是否仍開放。
- **證據／界線**：2026-10-11 真實本機再次同步海生館 30 筆：5 筆可公開、25 筆待審，新增一筆《SEA YOU》展期 2026-04-02 至 2026-06-28，在公開 API 為 `ended`；未增加當期展覽。48 項單元測試、型別檢查與隔離 PostgreSQL 整合測試通過。單次成功仍不證明跨週穩定，也不代表 25 筆待審是 25 場當期展。詳見[階段紀錄](stage-2026-10-11-nmmba-detail-dates.md)。

### ER-49｜館方活動預告與特展資料分流（規劃／來源已初查）

### ER-50｜奇美活動與節目的人工更新快照（已實作／本機驗證）

### ER-51｜奇美活動候選表的冪等匯入與異動歷史（已實作／本機驗證）

- **問題**：ER-50 的靜態快照能補出官網的工作坊與節目，但沒有可重跑的資料庫身份或欄位異動證據。直接將售票日、音樂節場次或「即日起」塞入 `exhibitions`，會製造錯誤起訖日。
- **處理**：新增 [`015_programme_events.sql`](../db/015_programme_events.sql)，建立與特展分開的 `programme_events`、`programme_event_changes`；候選身份為 `(museum_id,provider,source_type,source_event_id)`，資料庫 `UNIQUE` 加上交易 advisory lock 阻止重複與並行覆蓋。[`chimei-programmes.ts`](../src/chimei-programmes.ts)再驗證人工快照的來源、官方連結、ID 與文字；完整範圍可轉日期，其餘歸類 `multiple_dates`、`ongoing`、`time_only`、`unknown` 並保留原始時間文字與可空日期。`content_hash` 無變則只更新核對時間；有變則逐欄寫入歷史，同交易提交。完整度只與**上一份成功快照**的來源 ID 比較，不把保留的歷史缺席資料算進當期清單；舊快照、縮水達一半或來源 ID 大量替換時整批回滾。清單缺席不自動刪除或標取消。手動命令是 `npm run import:chimei:programmes`。
- **取捨**：採**通用候選活動表**，僅保留目前證實的核心欄位，沒有先把藝術家、策展人、表演廳、餵食秀等不同 Domain 的特有欄位塞入主表。沒有從含「啟售」的工作坊日期推論實際單一場次，也沒有把 `isfree` 字串當確定免費。網站目前仍讀人工 JSON 快照；資料庫候選不是已公開活動 API、來源健康成功或可持續奇美自動同步的證據。
- **證據／界線**：隔離 PostgreSQL 測試涵蓋 015 migration、重跑零新增、標題／日期欄位異動、舊快照與縮水回滾，以及連續換季時只比較上一份快照；單元測試涵蓋有效／無效日期、音樂節、售票日、長期及僅時段。2026-10-11 本機既有 DB 套用 1 份 migration，首次匯入 10 筆、同快照再跑 10 筆全部未變。`/chimei-activities.json` 靜態快照的回應已納入 OpenAPI 與實際 HTTP 契約測試，與資料庫候選表及正式活動搜尋分開。型別檢查、52 項單元測試及整合測試通過。仍須核對跨週來源穩定、官網數量涵蓋、更多欄位語意與使用條件，才可考慮自動同步或公開活動搜尋。

### ER-52｜國美館來源只收本館限期展，藝術欄位獨立建模（已實作／本機單日驗證）

- **問題**：國美館[當期展覽](https://www.ntmofa.gov.tw/News_Actives_photo.aspx?n=1462&sms=11893)同時列出臺中本館展、館外展、線上展、常設展及得獎名單公告。清單連到文化部 NTMOFA 逐筆頁，人物與相關活動資訊只有部分展覽明載。直接把清單當成全館限期展或用介紹段落猜測策展人會誤導訪客。
- **處理**：[`ntmofa.ts`](../src/sources/ntmofa.ts)讀官方當期與預告 HTML，抽取活動 ID、標題、完整日期與展區，必要時讀同一筆文化部 NTMOFA 詳情確認標題與本館場地；常設、公告、線上及館外項目保存最小來源紀錄並略過。第 [016 migration](../db/016_art_exhibitions.sql)將館所類型設為 `art_museum`，並以 `art_exhibition_details`、`art_related_events`、`art_exhibition_changes` 存人物、展覽類型、展區／樓層、活動連結與異動，不污染共通 `exhibitions`。匯入沿用來源鍵冪等、交易、完整度與待審流程；`/museums` 與 `/exhibitions` 暴露已確認欄位，React 展覽卡展開後可看人物與相關連結。
- **決策**：詳情頁連結是官方清單所用的文化部網站，**不是國美館公開文件化 API**。人物只擷取「參展藝術家」「策展人」等明確標籤；本次教育展雖有「展覽策劃」，其角色不等同策展人，`curatorNames` 仍留空。相關系列活動可能已結束，不推斷可報名。多個展廳跨樓層時 `floor=null`，保留原展區文字。官網頁面資料的重製限於必要標題、日期、場地、人物與官方連結，未下載影像或全文。2026-10-11 可見的 11 張當期卡與 1 張預告卡未見「下一頁」，但網站日後是否增加分頁、季節換展時來源鍵變化和跨週穩定仍待追蹤。
- **證據／界線**：2026-10-11 真實只讀探針看見 12 張卡，3 筆臺中本館限期展可核對，9 筆排除，0 筆待審；隨後本機 PostgreSQL 第 016 migration 成功、正式來源同步首次匯入 3 筆，`coverageStatus=baseline_created`。隔離整合測試驗證重跑冪等、藝術家變更歷史、相關活動關係、OpenAPI HTTP 回應；55 項單元、型別、React build 與整合測試通過。新版本機 3006 埠 API 確認 3 筆與教育展 3 位藝術家；舊 3000 埠程序仍可能提供舊欄位。尚未線上部署或啟用國美館週期排程，首次成功不代表穩定覆蓋；詳見[Phase 2 階段紀錄](stage-2026-10-11-phase2-ntmofa.md)。

### ER-54｜美術展欄位異動查詢（已實作／隔離資料庫驗證）

- **問題**：第 016 migration 已把藝術家、策展人、展區和相關活動變更寫入 `art_exhibition_changes`，但公開 `/exhibitions/:id/changes` 只查共通欄位，使用者與面試審查無法核對美術異動。
- **處理與決策**：增加 `GET /exhibitions/:id/art-changes`，延用展覽可見性與模擬資料規則，按偵測時間及流水號倒序取最近 100 筆。維持共通異動 API 的純字串契約；藝術欄位的 JSONB 值直接回傳字串、陣列或 `null`，以 OpenAPI `anyOf` 驗證不同欄位形狀。一般館所回空陣列，不把美術專用欄位塞進共通展覽模型。
- **證據／界線**：隔離 PostgreSQL 整合測試先匯入「甲藝術家」，再更新為「乙藝術家」，真實 HTTP 回應的 `artistNames` 舊／新陣列與資料庫一致；一般館所回空陣列。OpenAPI 成功回應驗證、56 項單元與型別檢查通過。本 API 是異動歷史，不代表使用者訂閱通知已實作。

### ER-65｜歌劇院官方清單獨立基準與縮水覆核（已實作／本機驗證）

- **問題**：先前歌劇院 `sampled_list` 同時收人工快照與官網 `place=1` 清單，無法可靠比較相鄰官方批次。若官網頁面異常只回少量節目，仍可能將殘缺批次當作正常匯入；但換季也可能自然減少節目，不能把缺席直接解讀為取消。
- **處理與決策**：第 [018 migration](../db/018_ntt_list_review.sql) 增加 `ntt_place1_list` scope 與 `domain_source_runs.review_note`。只有不帶 `--snapshot`／`--detail` 的官方清單同步使用新範圍。交易內以最近一次成功的同範圍批次為基準：至少 10 筆且新批次少於一半時，拋出 `SOURCE_ANOMALY` 並回滾全部事件變更。站長核對[館方清單](https://www.npac-ntt.org/program/events?place=1)後，若確屬正常變動，可用 `--review-shrink` 提供 20–500 字理由放行；理由隨成功批次保存。未觸發異常、人工抽樣或單筆詳情不得使用覆核說明。缺席資料不自動刪除或標示取消。
- **證據／界線**：隔離 PostgreSQL 整合測試驗證官方 19 筆基準→抽樣一筆→官方 9 筆拒收、原 20 筆 API 資料保留，以及人工覆核後成功並存入理由；66 項單元、型別與 React build 通過。本機 `npm run migrate` 新套用一份 migration，真實 `place=1` 清單以新範圍接受 20 筆（更新 1、未變 19）。舊 `sampled_list` 成功批次不混入新基準，因此這是新範圍的第一次成功；跨週穩定、其他篩選條件與逐場票務狀態仍待驗證。

### ER-66｜歌劇院同筆數大量換鍵也需覆核（已實作／本機驗證）

- **問題**：ER-65 只檢查筆數縮水；若官方頁仍有 20 張卡，但詳情連結幾乎全部更換，可能是正常換季，也可能是頁面／解析異常，不能直接當成健康同步。
- **處理與決策**：第 [019 migration](../db/019_domain_source_identity_keys.sql) 為 `domain_source_runs` 新增僅供 `ntt_place1_list` 使用的 `identity_keys`。每次官方批次在成功或失敗紀錄中保存排序後的來源鍵；只和最近一次**成功**、同範圍且已有來源鍵的批次比較。前後至少各 10 筆，重疊來源鍵少於較小清單的一半時，與大幅縮水共用 `SOURCE_ANOMALY` 回滾及 `review_note` 人工覆核。CLI 改以 `--review-list-change` 表達兩種異常，保留舊 `--review-shrink` 相容；沒觸發異常不能隨意附覆核說明。舊成功批次無鍵，第一次新版本同步只建立鍵基準，不回填或猜測歷史清單。
- **證據／界線**：單元測試涵蓋 20 筆中只保留 9／保留 10 的邊界。隔離 PostgreSQL 整合測試涵蓋官方 19 筆→同筆數換掉 10 個來源鍵而拒收、公開資料保持原狀、附理由放行，以及其後縮水 19→9 再拒收／覆核；67 項單元、型別、React build、隔離整合測試通過。本機第 019 migration 已套用；當日真實清單再次同步 20 筆全部未變，資料庫只讀核對最新成功批次 `accepted_count=20`、`identity_keys` 亦為 20，已保存首次來源鍵基準。這不是跨週穩定證據，也不表示其他篩選條件、逐場票務已驗證。

### ER-67｜表演清單預設只呈現尚未開始的有效場次（已實作／本機整合驗證）

- **問題**：歌劇院匯入保留歷史節目與異動資料，原 `/performances` 及首頁無時間篩選。場次過期後仍可能顯示在訪客的節目卡，且同節目的舊場次與未來場次混列。
- **處理與決策**：公開 API 的 `period` 預設 `upcoming`。以同一查詢時間篩選 `starts_at` 未到、狀態為 `scheduled` 或 `sold_out` 的場次；先依是否有合格場次篩節目，再計算 `total`、分頁及按最近場次排序，卡片只回傳合格場次。`period=all` 保留完整歷史及 `unknown`／取消／延期狀態供追查；此查詢不刪除或改寫資料。海生館每日觀察路徑不接受 `period`，避免把不同領域誤作相同時態。React 提示這仍非即時票務，並導向官網。
- **限制／驗證**：`scheduled` 不保證有票；`sold_out` 仍可見但不能暗示可購票。整個節目若從官網清單消失，匯入流程不會自動把所有舊場次標成 `unknown`；後續 ER-68 以成功清單來源鍵限制預設顯示，仍須看 `sourceCheckedAt` 並向館方核對。隔離 PostgreSQL 整合案例涵蓋混合新舊場次、未核對狀態、總數、排序、分頁及完整紀錄模式；2026-10-15 本機資料庫服務恢復後已通過。67 項單元、型別檢查與 React build 亦通過；此驗證不等於真實館方跨週穩定或即時票務。

### ER-68｜歌劇院缺席節目不再混入未來清單（已實作／本機整合驗證）

- **問題**：ER-67 排除過期及狀態不明的場次，但整個節目從下一次官方清單消失時，舊 `domain_events` 及未來 `scheduled` 場次仍保留，首頁可能繼續推薦。缺席可能是正常換季、篩選範圍或來源異常，不能直接判定取消。
- **處理與決策**：沿用 ER-66 已保存的 `ntt_place1_list.identity_keys`，不用新 migration，也不改寫節目狀態。`/performances` 預設模式對 `ntt` 取最近一次**成功且有來源鍵**的官方批次，只讓來源鍵仍在清單內的節目進入 `total`、分頁及卡片。已被 `SOURCE_ANOMALY` 拒收的批次與 `sampled_list`／`single_detail` 不改基準；尚無可用基準時維持 ER-67 時間及場次狀態篩選。`period=all` 繼續查完整歷史，以免缺席證據被抹掉。此規則僅限歌劇院 `place=1`，不套用海生館或其他來源。
- **限制／驗證**：這是**清單成員資格**，不是取消、售罄或來源即時性判定。隔離 PostgreSQL 整合案例測試首次基準、抽樣不污染、異常拒收維持舊清單、人工覆核後縮水及 `period=all` 保留缺席節目；合成場次改用相對未來日期，避免測試在固定日期後失效。測試資料使用文件允許的 `ntt` 來源鍵；2026-10-15 本機整合測試、67 項單元、型別檢查與前端編譯通過。未執行真實官網的新一輪同步，不宣稱跨週穩定。

### ER-69｜歌劇院作品簡介中的場次異動公告停止自動匯入（2026-10-15 已由 ER-70 取代）

- **問題**：館方[節目詳情](https://www.npac-ntt.org/program/events/c-kboz8xw2UFj)曾在「作品簡介」的醒目公告逐場說明兩場延期、一場取消，但一般標題與場次列表仍存在。原 Adapter 只檢查標題，會將列表中的場次一律標為 `scheduled`；既無逐場狀態證據，也可能讓訪客以為異動場次照常演出。
- **處理與決策**：`parseNttDetail` 繼續攔下標題中的取消／延期／異動，並額外檢查 `SortIntroduction` 內 `callout` 的明確異動字樣。一旦命中，停止該批同步、不寫入未核對的場次；`sync:domain` 錯誤附上對應館方詳情網址，供站長逐場核對。沒有從公告文字猜測新時間或把全部場次一律標成取消；之前成功資料與清單基準保留。
- **證據／界線**：2026-10-15 唯讀核對上列館方頁的 HTML，公告位於 `SortIntroduction` 的 `callout`，包含逐場延期及取消敘述；單元測試涵蓋標題「活動取消」、內文部分場次異動，以及無明確異動公告仍可解析。68 項單元與型別檢查通過。此規則只覆蓋已確認的標題和公告版位；館方若移動公告或只在售票系統改狀態，仍可能漏判。沒有建立逐場售罄／取消／延期自動狀態，也未重新執行整批真實來源同步。

### ER-70｜歌劇院逐場核對與異動隔離（已實作／本機整合驗證）

- **問題**：ER-69 的整批停止雖避免誤刊，卻讓單一含異動公告的節目卡住其他正常節目；館方按鈕也可能明示全節目「已額滿」，原 Adapter 仍一律標 `scheduled`。沒有逐場有證據的人工核對途徑，取消／延期欄位便只是資料模型上的空殼。
- **處理與決策**：來源 Adapter 若在標題或已確認的 `SortIntroduction.callout` 看見異動公告，將該節目全部場次設為 `unknown`；預設 `/performances` 排除，其他節目照常匯入。只有館方詳情的報名按鈕**完整標示**全節目額滿／售罄時才把所有場次設 `sold_out`，不從介紹文字或「部分場次完售」猜票況。第 [020 migration](../db/020_performance_session_reviews.sql)保存場次狀態來源、官方證據網址、核對人、說明與時間；第 [021 migration](../db/021_session_review_source_version.sql)把人工結論綁定核對時的來源內容雜湊。`review:performance pending|set` 讓站長查看未來待審場次、以同節目詳情或官方新聞逐場核對；交易內與來源匯入共用 advisory lock、相同核對冪等，狀態改變寫入 `domain_event_changes.sessionStatus`。同一來源版本再次同步保留人工狀態；若官方內容變動，舊核對結論失效，一般場次回 `unknown`，明確全額滿則取館方 `sold_out`，並待重新核對。場次從詳情消失亦改回 `unknown`。API 回傳狀態來源／證據／核對時間，React 可檢視即將演出或包含取消、延期與歷史資料的完整紀錄。
- **證據／界線**：2026-10-15 唯讀實測[官網「已額滿（需後補）」頁](https://www.npac-ntt.org/program/events/c-NIh2qmoeYT7)解析兩個 `sold_out` 場次；[部分場次異動頁](https://www.npac-ntt.org/program/events/c-kboz8xw2UFj)解析四個 `unknown` 場次。單元測試涵蓋全額滿與部分完售區別、公告隔離；隔離 PostgreSQL／HTTP 整合測試涵蓋同批正常節目照常匯入、`unknown` 不公開、逐場核對後只公開正常場、取消場留在 `period=all`、人工證據可讀、重複核對、同版同步保留結論與官方內容變動後舊結論失效。當日早些時候官網 `place=1` 本機手動同步接受 20 筆、全部未變；本階段沒有即時逐場票務來源，不能推定 `scheduled` 有票，也不能宣稱所有館方公告版位已覆蓋。官網篩選範圍只限 `place=1`，跨週穩定仍需後續實際觀察。

### ER-71｜海生館指定日期開館只接受官方證據覆核（本機已驗證）

- **問題**：館方平常營業時間和假期例外寫在同一服務頁；平常週二休館也有國定假日、連假與寒暑假例外。官網當日節目表不能證明未來指定日期一定開館。導覽頁仍沿用舊的分月時間。
- **決策**：依 2026-10-15 [館方服務頁](https://www.nmmba.gov.tw/cp.aspx?n=A6476B49BA86BBD5&s=B3CCAAE6060F5DB7)修正平常時間。第 022 migration 以單日、官方佐證、開／休館及時間建立人工覆核表，另留異動歷史；相同內容覆核冪等。`visit-status` 只有存在該日核對紀錄才回 `open`／`closed`，否則維持 `unknown` 並提示平常規則及官網。不能從週二或節目表推斷。
- **證據／限制**：10/15 官方節目表再接受 9 筆，型別、單元、React build 及隔離 PostgreSQL／HTTP 整合驗證。特別開館測試使用合成資料，正式資料庫未新增任何虛構日期。無完整官方逐日行事曆及跨週觀察；不宣稱 P4 已完成。見[階段紀錄](stage-2026-10-15-phase4.md)。

### ER-72｜海生館每日節目保存有日期的完整成功快照（本機已驗證）

- **問題**：原 `domain_events`／`recurring_schedules` 只保存各節目的最近時段。隔日或同日場次修改後，舊日完整清單與當時未變的節目都無法重建；僅靠欄位異動紀錄不足以比較兩天的整體節目。
- **處理與決策**：第 [023 migration](../db/023_marine_daily_observations.sql) 依來源、觀察日期、內容雜湊保存完整 JSON 快照，內容只放正規化後的節目與時段，不存整頁 HTML。`importDomainEvents` 要求同批海生館資料同日，在既有來源鎖與交易內寫入快照；同日同內容只更新 `last_seen_at`，內容改變另留版本。`SOURCE_ANOMALY` 或其他失敗整批回滾，不得產生快照。`GET /marine-programmes?date=` 取該日最後成功版本；`GET /marine-observation-days` 列可查日期與版本數。無日期的 API 維持最近成功清單。前端提供日期切換及與最近成功觀察的節目／時段增減對照；缺席僅表示該次節目表未列出，不判定取消。
- **證據／界線**：隔離 PostgreSQL／HTTP 整合測試驗證 10/12 舊時段於 10/13 更新後仍可查、同日不同內容兩版、同日重跑不增版、10/15 異常縮水不進快照，以及日期／分頁 API 契約。單元測試另驗證新增／缺席／時段變動對照及不修改原始快照。70 項單元、型別、React build、整合測試通過；本機第 023 migration 已套，10/15 官方當日表再次同步接受 9 筆，建立第一份正式快照。更早的資料**未回填**，沒有跨週穩定觀察、趨勢圖或未來場次預測。詳見[階段紀錄](stage-2026-10-15-phase4.md)。

### ER-73｜海生館清單縮水或大量換鍵須有證據才能覆核（本機已驗證）

- **問題**：原海生館 `daily_page` 只防筆數大幅縮水；同筆數但節目來源鍵幾乎全換可能是解析異常，會錯誤接受。反之，館方若真有特殊日大幅縮減，原來沒有可追溯的人工放行管道，可靠資料也會一直被拒。
- **處理與決策**：沿用上次**成功**官方清單筆數作縮水基準，第 [024 migration](../db/024_marine_daily_review.sql) 擴充 `domain_source_runs.identity_keys` 允許 `daily_page`，另存 `review_evidence_url`、`reviewer`；既有 `review_note` 保存原因。前後至少各 4 筆且來源鍵重疊少於較小清單一半時，與少於上次筆數一半共用 `SOURCE_ANOMALY`。預設整批回滾並保留最新資料及每日快照；站長逐項核對館方當日頁後，可在**官方直接同步**附說明、館方 HTTPS 網址與核對者。交易內再次檢查異常仍存在才放行，成功批次保留來源鍵、證據和快照。人工快照、無異常批次、非官方證據均不能使用覆核。程式只能限制證據網域，不能證明內容與結論相符；正常特殊日仍需人核對。
- **證據／界線**：隔離 PostgreSQL／HTTP 案例涵蓋同筆數全換鍵拒收、非官方證據拒收、人工覆核後來源鍵與證據留痕、無異常拒絕多餘覆核、縮水拒收及有證據放行後建立日期快照。71 項單元、型別與整合測試通過，第 024 migration 已套本機；案例中的來源頁、日期與異常是合成測試，沒有真實特殊日放行。舊成功批次不回填來源鍵，下一次成功官方同步才建立首次基準。跨週穩定及官方清單完整性仍待觀察。見[階段紀錄](stage-2026-10-15-phase4.md)。

### ER-74｜以領域外鍵守住表演與海洋節目的時間模型（本機已驗證）

- **問題**：`domain_events` 已區分 `performance` 與 `marine`，但 `event_sessions.event_id`、`recurring_schedules.event_id` 原本只參照父資料的 `id`。資料庫能接受海洋節目的表演場次或表演節目的每日時段；這會讓後續查詢及異動解讀出現矛盾。
- **處理與決策**：第 [025 migration](../db/025_domain_child_integrity.sql)新增父表 `(id,domain)` 唯一鍵，兩種子表各以固定領域的 `domain` 欄位及複合外鍵參照父表。現有匯入由資料庫預設填入固定值，來源識別不寫死，因此後續不同館的同類節目可沿用。保留限期展的日期範圍、美術館延伸表、表演逐場時間與海洋當日觀察四種時間模型；不建立一張大量可空欄位的共用 `events` 表。完整對照見[模型文件](domain-model.md)。
- **證據／界線**：隔離 PostgreSQL／HTTP 整合測試驗證兩種跨領域子資料寫入都以外鍵錯誤拒絕，已有表演場次的父節目也不可換成海洋領域；原有匯入、API 契約仍通過。71 項單元、型別檢查通過，第 025 migration 已套本機。這是關聯完整性，不等於來源正確或已完成跨領域搜尋；Phase 6 其餘模型契約仍需後續驗證，沖繩 Phase 5 暫停。

### ER-75｜現有 Domain Adapter 來源與領域在匯入入口明確配對（本機已驗證）

- **問題**：TypeScript 的 `PerformanceEvent | MarineProgramme` 只能限制開發時呼叫；執行時收到錯誤的 `sourceId`／`domain` 組合或未知來源，原匯入入口可能先建立批次紀錄，甚至繼續嘗試寫入錯誤領域。第 025 migration 保護子表關聯，但不驗證來源 Adapter 的身分。
- **決策**：在 `importDomainEvents` 的批次前置驗證要求目前 `ntt → performance`、`nmmba → marine`，拒絕未知來源或混入的領域；原有 scope 規則保持。這是現有 Adapter 的入口規則，資料庫本身仍不寫死來源，日後新增來源必須連同契約與測試擴充。
- **證據／界線**：隔離 PostgreSQL 整合測試送入錯配及未知來源，兩者皆在建立 `domain_source_runs` 前拒絕；既有表演、海洋匯入及公開 API 契約保持通過。此檢查不能替代官方資料內容核對，也沒有新增跨領域搜尋。

### ER-76｜公開節目回應採分型契約，避免時間語意被 nullable 欄位掩蓋（本機已驗證）

- **問題**：原 OpenAPI `DomainEvent` 把 `observedOn`、`sessions`、`dailySchedule` 都設為可空。即使 API 查詢把表演與海洋分開，契約測試仍會接受表演帶海洋日期、海洋帶表演場次，或端點回錯領域的資料。
- **決策**：保持現有 JSON 不變，將 `DomainEvent` 改成 `PerformanceEvent | MarineProgramme` 的 `oneOf`，以 `domain` 區分；表演只能有逐場 `sessions`，海洋節目只用觀察日與 `dailySchedule`。`/performances` 與 `/marine-programmes` 各自引用對應的清單型別。測試用 OpenAPI 驗證器加入 `oneOf` 恰好符合一個分支的檢查；未支援的 `not` 仍明確拒絕，避免文件形同虛設。
- **證據／界線**：單元契約測試涵蓋正確兩型、錯置日期／場次、錯端點回應；隔離 PostgreSQL／HTTP 整合測試驗證既有真實查詢形狀仍符合新契約。未建立跨領域搜尋 API，沖繩來源依指示暫停；新增其他來源時須連同分型契約調整。

### ER-77｜深海探勘分館呈現與沖繩靜態來源邊界（本機已驗證）

- **問題**：原深海探勘只顯示海生館每日節目，海生館限期展留在通用特展搜尋，沖繩既沒有圖鑑頁也沒有節目線索。若直接將沖繩人工核對時刻混入 `/marine-programmes`，會讓訪客誤以為它和海生館每日成功匯入資料具備相同新鮮度。
- **決策**：React 深海區分成屏東海生館與沖繩美麗海兩個館所區。海生館限期展透過既有 `/exhibitions?museum=nmmba&status=active` 在此區呈現，通用搜尋仍保留可尋性；每日餵食／解說沿用 `/marine-programmes` 的成功觀察日與歷史快照。生物圖鑑先採人工精選、連結館方條目的輕量版本：屏東三組、沖繩兩組；沖繩保留館方學名，均不把圖鑑條目當成當日展示保證。沖繩另有靜態館所介紹與館方節目頁人工核對快照；只記日本當地時間、核對日期、例外與官方連結，不寫入 `domain_events`，也不宣稱已完成日文 Adapter、每日同步或跨國模型驗證。未批量抓取或永久保存館方生物圖像，照片僅採 Wikimedia Commons CC BY-SA 4.0 縮圖並列明攝影者與授權。
- **來源／限制**：沖繩官方[樓層圖](https://churaumi.okinawa/en/area/floormap/)、[黑潮餵食](https://churaumi.okinawa/en/program/aquarium/kuroshio/)、[海豚劇場](https://churaumi.okinawa/en/program/surrounding-area/1459390261/)、[開館時間](https://churaumi.okinawa/en/guide/hour/)、[交通](https://churaumi.okinawa/en/guide/access/)與[生物圖鑑](https://churaumi.okinawa/sp/tc/fishbook/)於 2026-10-16 人工核對；海生館生物條目依館方展區頁整理。時段可變，沖繩 2027/01/04–01/09 海豚秀有已公告暫停。72 項單元、型別、React build 與隔離 PostgreSQL／HTTP 整合測試通過；本機瀏覽器核對到兩檔海生館限期展與沖繩區塊。跨日來源穩定性仍未建立。

### ER-78｜生物圖鑑照片與沖繩核心常設展區（本機已驗證）

- **問題**：深海探勘的五張生物卡片只有文字，沖繩的三段核心展區也只在館所介紹頁散列，訪客無法在主畫面循樓層探索。若把外地物種照片誤標為館內紀錄，或將常設展區冒充有展期的特展，會誤導行程安排。
- **決策**：五張卡片加入可查作者與 Creative Commons 授權的 Wikimedia Commons 縮圖，本站靜態路由供圖，卡片直接註明「野外／他館物種示意」或「過往館內展場紀錄」，並連到原圖；完整攝影者與授權集中在[照片來源頁](../web/photo-credits.html)。沖繩區加入依官方樓層圖排序的「珊瑚之海 3F → 黑潮之海 2F → 深海 1F」核心常設展區，逐區連回館方介紹。它們只作靜態參觀導覽，不進限期展 API，也不推定當日展示物種。
- **來源／限制**：[館方樓層圖](https://churaumi.okinawa/en/area/floormap/)及[珊瑚之海](https://churaumi.okinawa/en/area/the-coral-reef/coral-sea/)、[黑潮之海](https://churaumi.okinawa/en/area/the-kuroshio/kuroshio/)、[深海](https://churaumi.okinawa/en/area/the-deep-sea/deep-sea/)用於展區敘述；生物照片授權逐張列在照片來源頁。照片不代表 2026/10/16 的活體狀態。72 項單元測試、型別、React build、隔離 PostgreSQL／HTTP 整合測試通過，整合測試確認五張照片與來源頁可由服務載入。沖繩仍不是自動資料來源。

### ER-79｜化石探勘以分館靜態導覽與可追溯圖鑑起步（本機已驗證）

- **問題**：原站有海洋生物圖鑑與兩館深海分區，化石主題只有科博館的零散照片，無法讓訪客比較澎湖化石館與左鎮化石園區。若直接把常設展廳放進限期展 API、從新聞發布日猜活動場次，或把其他館的化石照片當成現場館藏，會製造錯誤行程資訊。
- **決策**：在 React 新增獨立「化石探勘」，以兩館切換呈現常設展區、行前資訊與每館兩筆化石圖鑑；另建兩篇可直接連結的館所介紹。澎湖三大主題按[縣府文化局館舍頁](https://www.penghu.gov.tw/phhcc/home.jsp?id=115)及[縣府公報](https://www.penghu.gov.tw/uploaddowndoc?file=govpaper%2F202512111255320.pdf&filedisplay=%E6%BE%8E%E6%B9%96%E7%B8%A3%E6%94%BF%E5%BA%9C%E5%85%AC%E5%A0%B1114%E5%B9%B4%E7%AC%AC12%E6%9C%9F.pdf&flag=pdf)整理；左鎮五大展館與化石館樓層按[園區官網](https://fossil.tnc.gov.tw/)及[化石館頁](https://fossil.tnc.gov.tw/content/index.php?m2=58)整理。當時澎湖古鱷使用本站線條示意並明標非標本照片，已於 2026-10-16 依 ER-82 改為縣府展場照片；澎湖水道古菱齒象齒化石雖相關，攝於臺北他館，在卡片與署名頁都標明。左鎮早坂犀、臺灣古鱷照片為可追溯授權的過往園區紀錄，不推定今日展出。布氏鯨是骨骼標本，放展區敘述但不混入化石圖鑑。
- **來源衝突與限制**：[澎湖文化局館舍頁](https://www.penghu.gov.tw/phhcc/home.jsp?id=115)寫週四至週一，[服務時間頁](https://www.penghu.gov.tw/phhcc/home.jsp?id=67)則對週二另有說法；前端不自選較「新」的規則，而明示週二需再確認。兩館沒有完成可靠的當期活動清單驗證，因此只連館方公告，不建立可搜尋限期展、活動場次、票價、指定日開館或自動同步。圖像按各 Wikimedia 檔案頁所列 CC0／CC BY-SA 授權使用 960px 縮圖，來源、攝影者與裁切資訊見[照片署名](../web/photo-credits.html)。
- **驗證**：2026-10-16 型別檢查、72 項單元、React build 和隔離 PostgreSQL／HTTP 整合測試通過；整合測試讀取兩篇館所頁與四張化石照片。這只證明本機功能與路由，不證明跨日來源穩定或官方清單完整。

### ER-80｜深海雙館改用明確切換（本機已驗證）

- **問題**：深海探勘原本以頁內錨點串接屏東、沖繩，訪客需要往下捲很遠才能找到另一館，兩館不同更新方式的資訊也容易混讀。
- **決策**：React 以 `selectedMuseum` 控制兩個館所面板，一次只掛載一館；按鈕使用 `aria-pressed` 表示選取狀態，窄畫面直排。海生館的深度導覽只在屏東面板顯示。切換按鈕同步更新網址錨點，初次載入及 `hashchange` 會辨識 `#sea-okinawa*` 等既有深連結，保留館所介紹返回圖鑑的路徑。兩館內容與資料取得邏輯不變：屏東繼續使用展覽及節目 API，沖繩仍為人工核對的靜態導覽。
- **驗證**：2026-10-16 型別檢查與 React build 通過；本機瀏覽器核對雙向切換、每次只顯示一館、沖繩圖鑑舊錨點與手機按鈕畫面。沒有修改後端、資料庫或來源匯入契約。

### ER-81｜Migration 帳本必須是本機版本的連續前綴（本機已驗證）

- **問題**：原 runner 會逐筆檢查已記錄版本的 checksum，但若帳本包含本機沒有的版本，或中間缺少已套用記錄，仍可能略過未知版本或逆序補跑舊 SQL。這會讓不同程式版本對資料庫結構有錯誤假設。
- **決策**：啟動時先驗證 SQL 檔從 `001` 連號；讀取帳本後要求已套用檔名恰為本機版本的前綴。未知版本與中途缺版立即停止，由維護者先確認程式與資料庫版本；原有 checksum 驗證及單版交易回滾維持。隔離 PostgreSQL 整合測試注入未知版、缺版與壞 checksum，確認 runner 拒絕，再還原帳本驗證可正常重跑。
- **限制／驗證**：這是防止版本漂移，不會自動修復資料庫；`--baseline-existing` 仍要求事前備份及結構核對。2026-10-16 型別、72 項單元、React build 與隔離 PostgreSQL／HTTP 整合測試通過，詳細覆蓋與未驗證項見[Phase 7 紀錄](stage-2026-10-16-phase7.md)。

### ER-82｜潘氏澎湖鱷圖像改採可追溯的縣府展場照片

- **問題**：原圖鑑只有線條示意；使用者提供的兩張新聞或來源未明照片未能確認可重製授權，未來若加入廣告，單純標註「示意」或保留浮水印不足以取得使用權。
- **決策**：使用[澎湖縣政府 2025 年新聞頁](https://www.penghu.gov.tw/ch/home.jsp?act=view&dataserno=202503120002&id=10087)刊出的潘氏澎湖鱷骨架照片，依[縣府網站資料開放宣告](https://www.penghu.gov.tw/ch/home.jsp?id=10299)在圖鑑、館所卡片及署名頁標示來源與授權。只使用確實拍到鱷骨架的第一張；同頁另一張為鯨骨，不作鱷類圖像。本站保留原始 JPG，卡片僅依版面顯示裁切，並明示是 2025 年展場紀錄，非今日展件保證或縣府背書。
- **界線**：開放宣告排除個別標示須取得同意的作品；目前該新聞頁未見照片個別限制，若來源方日後補充權利資訊須重新核對。這項查核不涵蓋網站其他照片，也不代表所有新聞媒體圖像可重用。
- **驗證**：2026-10-16 人工核對下載影像確為潘氏澎湖鱷骨架，照片標註與原始頁相符；TypeScript 型別檢查、React build 和 72 項單元測試通過。尚未聲稱已完成正式站台上線或廣告收益的整站授權稽核。

### ER-83｜本機靜態圖片路由與執行版本同步（本機已驗證）

- **問題**：化石照片檔案與 `src/server.ts` 路由已存在，但 4101 執行的是新增路由前啟動的舊 Node 程序，頁面請求圖片時回傳 404；`preview.cjs` 也缺少後來加入的化石館、深海與館所圖鑑靜態路由。
- **決策**：核對 4101 的程序屬於 Event Radar 後重新啟動，讓目前程式碼提供圖片。同步補齊預覽服務的兩館介紹頁、照片來源頁及後續新增的靜態圖片路由。只處理本機服務與白名單，沒有更改照片來源或建立自動匯入。
- **驗證／界線**：本機瀏覽器確認澎湖鱷 1477×1108、古菱齒象 960×720、左鎮早坂犀 960×720、臺灣古鱷 960×590 均正常解碼；兩篇館所介紹主圖與館所圖鑑卡片亦可顯示。這是目前 4101 的本機驗證，沒有證明未來部署環境或所有外部照片皆正常。

### ER-84｜作品集文件以已驗證能力與資料來源等級為主軸（Phase 8）

- **問題**：README 與來源盤點仍以早期五館特展為主，沒有把後續歌劇院多場次、海生館每日觀察、沖繩與化石館靜態導覽分開。舊架構文字也曾稱沖繩暫停，和目前靜態頁不一致；面試時容易把本機 Adapter、人工快照與上線運作混為一談。
- **決策**：README 第一屏先給目前能力／資料邊界與閱讀路徑；[架構圖](architecture.md)區分限期展、表演／海洋節目與人工靜態導覽；[ERD](erd.md)只畫實際外鍵並說明領域時間模型；[來源盤點](sources.md)按本機同步、候選及靜態導覽分類。[面試介紹](portfolio-brief.md)只採有日期的本機測試與同步證據，拒絕虛構公開網址、流量、營收或線上 SLA。API 的人類可讀清單與既有 OpenAPI 保持一致。
- **證據／界線**：交付文件與連結檢查記於[Phase 8 驗收](stage-2026-10-16-phase8.md)。本次沒有新增來源、資料庫表、公開 API 或部署；先前 Phase 7 的測試結果仍只證明當時的本機功能，文件整理不能替代正式環境 smoke test。

### ER-85｜公開測試版採同源服務與可明確關閉索引的部署準備（本機已驗證，未上線）

- **問題**：原 `start` 會在啟動前重建 React，HTTP 只綁本機位址，沒有可重現的部署後檢查。若免費預覽服務被搜尋引擎誤收錄，或新資料庫只有館所資料卻對外宣稱展覽可查，也會造成作品集與訪客的錯誤期待。
- **決策**：第一版以單一 Node Web Service 同源提供 React 與既有 API，資料庫用獨立 PostgreSQL；保留本機 `127.0.0.1` 預設，部署時明設 `HOST=0.0.0.0`，由平台注入 `PORT`。`start:prod` 只啟動已建好的頁面；`render.yaml` 固定免費技術預覽、手動部署及外部 `DATABASE_URL` Secret，不建立管理服務或 Queue。`PUBLIC_BASE_URL` 未設時，回應 `X-Robots-Tag: noindex`，並允許爬蟲讀取該標頭、不提供 sitemap；設定成最終 HTTPS 根網址後才為首頁及既有靜態館所介紹輸出 canonical 和 sitemap。動態展覽沒有獨立 HTML 頁，不加入 sitemap。`smoke:deploy` 唯讀檢查 health、bundle、資料 API、介紹頁及照片，預覽時以 `--expect-noindex` 另檢查標頭。
- **取捨／故障模式**：Render 免費 Web Service 閒置休眠，休眠時平台代回 `Disallow: /` 的 `robots.txt`，爬蟲可能看不到本站的 `noindex`；預覽並非私有環境，因此不宣稱絕對不收錄、自然搜尋或持續可用。此階段原規劃由站長在本機執行 migration 與第一次官方匯入，2026-10-17 因免費 Render 不提供獨立部署前指令而由 ER-86 改為建置時執行。`render.yaml` 匯入後才會建立公開服務。程式版本以 Render 部署 SHA 核對，沒有內建公開 SHA 端點；資料庫 schema 回退需另行備份與計畫。
- **驗證**：2026-10-16 型別、72 項單元、React build、隔離 PostgreSQL／HTTP 整合及本機 smoke 通過；整合測試確認 `PUBLIC_BASE_URL` 下的 canonical、robots、sitemap。詳見[部署手冊](deployment.md)與[階段紀錄](stage-2026-10-16-phase9-prep.md)。尚未建立 Neon／Render 帳號資源、遠端 migration、公開網址或真實流量。

### ER-86｜免費預覽的資料庫初始化移到受控建置步驟（遠端已驗證）

- **問題**：Render 免費 Web Service 沒有獨立 pre-deploy command 或 dashboard shell；Neon 新資料庫無 schema／展覽，若直接匯入既有 Blueprint，服務即使啟動也會提供空白特展。Neon MCP 的第二段 OAuth 要求整個帳號的專案與組織建立／刪除權限，超出單一專案授權需求，因此沒有核准。
- **決策**：免費技術預覽先於 `render.yaml` 建置順序完成 React build，再執行有 checksum 帳本及 advisory lock 的 `npm run migrate`，最後執行 `scripts/bootstrap-preview.mjs`。此腳本只有在資料庫沒有可公開、未結束限期展時，才依序嘗試故宮北院、科工館、故宮南院現有官方 Adapter；每個來源失敗與下一個隔離，取得至少一筆合規資料便停止。全數失敗時拒絕發布空白站。Neon 連線字串只交給 Render Secret，另依站長要求存一份在 Git 忽略的本機 `private/`，不在已追蹤文件、Git 或對話傳遞。後續資料更新仍由手動同步，不宣稱已上線定時排程。
- **取捨／故障模式**：免費建置可能在 migration 套用後因來源或服務啟動失敗，因此 schema 變更要向後相容，後續部署前仍須備份；此做法不是正式環境的長期 migration 流程。已有展覽時建置不自動更新來源，需另行檢查資料新鮮度。首次匯入的三個來源不保證永遠有未結束的合規展覽，失敗時保持未發布狀態。
- **驗證**：2026-10-17 Render 對部署 `8d78297` 的建置套用 25 份 migration，科工館已先在 Neon 匯入 7 筆未結束展覽，因此首次資料檢查通過，服務顯示 Live。其後完成更多手動匯入，線上 `smoke:deploy --expect-noindex` 通過，結果為 11 間館所、27 筆可搜尋特展。Render 自身連故宮北院來源三次失敗，不能把本次成功解讀為 Render 可穩定自行同步全部來源；詳見[部署紀錄](deployment.md)及 ER-87。Render 免費方案限制以[官方部署文件](https://render.com/docs/deploys)核對。

### ER-89｜Search Console 以建置環境注入驗證標記（線上已驗證）

### ER-91｜雲端來源按館隔離，故宮北院暫停自動抓取（六工作手動驗證）

- **驗證與後續**：2026-10-17 手動執行 [#3](https://github.com/AndyLinStrongtyping/event-radar/actions/runs/39032657980) 中，科博館、故宮南院、海生館、科工館、國美館、歌劇院六個工作成功；北院 `fetch failed`。合併隔離開關後再手動執行 [#4](https://github.com/AndyLinStrongtyping/event-radar/actions/runs/39033250246)，六工作成功、北院依設定略過。Render 重新部署後 `/health` 回報網站與資料庫皆 `ok`。這證明手動工作流程可運作，**尚未證明實際週二觸發或跨週穩定**；需持續觀察真實排程，並查證北院可用的雲端官方來源後才重新啟用該館。

### ER-92｜長頁面提供浮動回頂操作（公開站瀏覽器已驗證）

- **問題**：朋友在手機上閱讀長篇首頁時，滑到深海、化石及館所區後，要回頂端導覽需往上滑很久；館所導覽頁也有相同問題。頁尾既有回頂連結只有到頁尾才看得到。
- **決策**：首頁 React 與 14 篇靜態館所頁都在捲動 600px 後顯示固定回頂按鈕。維持原有導覽列，不增加常駐雙排導覽。按鈕採 50px 點擊範圍、鍵盤焦點框與無障礙名稱；依系統減少動態效果設定切換平滑或立即捲動，列印時隱藏。靜態頁共用 `/back-to-top.js`，避免每頁複製事件處理。
- **取捨／驗證**：按鈕由捲動事件控制，頁首隱藏，避免長駐遮擋；瀏覽器不支援 JavaScript 時保留既有頁面導覽。本機 Chrome 實測發現平滑回頂途中若在 600px 門檻立即隱藏按鈕，捲動可能停在半途，因此點擊後保留按鈕至 `scrollY <= 1`。React 首頁及澎湖、海生館導覽頁在本機可回頂；`npm run typecheck`、`npm run build:web` 及文件連結檢查通過。2026-10-18 PR #2 合併、CI 通過後，Render 因自動部署關閉而手動部署 `52d803c`；公開首頁及澎湖導覽頁皆實測從頁面下方回到 `scrollY=0`，按鈕隱藏，`/health` 回 `status=ok, database=ok`。手機實機手感及其餘 13 篇頁面尚未逐頁驗證。

### ER-93｜故宮北院本機更新與雲端連線診斷（自動排程仍暫停）

- **觀察**：2026-10-18 同一個 `odapi.npm.gov.tw` 官方 JSON 來源以本機 Node 取得 HTTP 200；以本機已保存的資料庫連線重新同步 Neon，取得 22 筆來源列，1 筆既有可公開展覽未變、15 筆待審、6 筆略過，來源鍵與上次 22 筆基準一致。GitHub Actions #3 與 Render 先前均在連線階段報籠統的 `fetch failed`；未能由這些紀錄判定 DNS、TCP、TLS 或來源端限制。文化部[展覽資訊開放資料](https://data.gov.tw/dataset/6012)同日只有 1 筆故宮相關展覽，與目前可公開的故宮 JSON 展名及展期一致，但沒有故宮逐筆網址，也不能證明完整覆蓋。
- **處理**：`fetchSource` 捕捉連線錯誤，只輸出預期來源主機與格式受限的網路錯誤代碼，不輸出可能含憑證的原始 URL 或錯誤訊息；既有有限重試仍辨識此類錯誤。保留 `EVENT_RADAR_NPM_NORTH_SYNC_ENABLED` 為非 true，並以本機人工執行作為暫時更新流程。文化部資料只用於交叉核對，沒有冒充故宮完整來源、建立重複展覽或推進故宮最後成功時間。
- **驗證與界線**：PR #3 的一次性 GitHub Actions 唯讀探測，使用同一 Node 24 `fetch`、User-Agent 與 15 秒逾時設定，得到 `TypeError`／`UND_ERR_CONNECT_TIMEOUT`；CI 其他型別、單元與 PostgreSQL 整合檢查通過。已移除一次性探測步驟，避免以館方可用性決定正常 CI 成敗。此結果只證明 GitHub runner 到該主機建立連線逾時，不能斷言館方封鎖或判定 Render 完全相同原因。若需要無人值守北院來源，應向資料提供機關確認可供雲端使用的官方出口，並再做跨週實測；否則維持明確標示的人工更新。不得以繞過保護措施、未驗證的第三方鏡像或文化部不完整清單偽裝成自動同步。**目前沒有恢復故宮北院每週自動更新**。

### ER-94｜先驗證備份能還原，再進行後續正式資料庫變更（正式資料已完成單次本機演練）

- **問題**：公開站已使用 Neon PostgreSQL，而 Render 建置會執行 migration；只有資料庫連得上及 CI 通過，不能保證資料遺失或錯誤 migration 後可復原。Windows 工作站原本沒有原生備份工具，專案資料夾又位於 OneDrive。
- **決策**：使用與伺服器主版本相容的 PostgreSQL 原生 custom-format `pg_dump`，把密碼放在子程序環境變數而非命令列；預設備份目錄是 Git 忽略的 `private/backups/`，正式備份改由 `EVENT_RADAR_BACKUP_DIR` 指向非 OneDrive 的本機 AppData。留下大小與 SHA-256。還原只接受明確命名的獨立空白庫及所設備份目錄內的 `.dump`，`pg_restore --single-transaction --exit-on-error` 後查 migration 帳本及主要資料表。CI 使用 PostgreSQL 17 和合成資料測試，不把正式 Neon 內容上傳 CI artifact。
- **驗證與界線**：`test/db-backup.test.mjs` 的連線解析及還原目標防護通過，連同既有單元測試共 74 項；[GitHub CI #50](https://github.com/AndyLinStrongtyping/event-radar/actions/runs/39101962456) 還原合成展覽、來源及異動關係。2026-10-18 Neon 實測版本為 18.6，17.11 的 `pg_dump` 因主版本不相容而失敗；換用 18.6 後產生 146,102 bytes 備份，SHA-256 `8074b679838dc3ad83eb797db2540e9ad4403d2e4ddcddd366af67cbcf532222`。本機隔離還原後，25 份 migration、11 間館、30 筆展覽及 18 筆匯入紀錄與 Neon 唯讀筆數一致，臨時庫已停止並清除。這是**單次本機驗證**，尚無加密異地副本、定期輪替或正式復原演練；不能視為完整災難復原。正式還原不得直接覆寫原庫。操作及環境問題見[演練紀錄](stage-2026-10-18-neon-backup-drill.md)。

### ER-95｜靜態快速前端與休眠 API 分離，保留同源站為 canonical（公開環境已驗證）

- **問題**：Render 免費 Web Service 閒置後會休眠；React、CSS、圖片與 API 原本都由同一服務提供，訪客第一次開站會先等待後端喚醒，無法像純 GitHub Pages 網站立即看到介面。
- **決策**：保留 Render 為 canonical 網址、Node 唯讀 API、靜態館所頁與 Neon 入口；另由 GitHub Pages 發布編譯後的 React 應用外殼及公開圖片。`VITE_BASE_PATH` 處理專案子路徑，`VITE_API_BASE_URL` 只把資料請求與館所介紹導向 Render。公開服務沒有 Cookie、登入或寫入 API，故回應 `Access-Control-Allow-Origin: *` 供 Pages 跨來源 GET；整合測試固定這項契約。Pages 建置注入既有 GA4、`noindex,follow` 並把 canonical 指向 Render，避免兩個入口被當成兩套主要搜尋頁面。現有 Render 同源站維持可用，Pages 失敗不會移除原站。
- **取捨／限制**：頁面結構、互動程式及圖片能由 CDN 先出現，但展覽、票務館所清單、節目及資料狀態仍需等待 Render API；這改善首次可見畫面，沒有消除免費後端冷啟動，也不是高可用架構。館所介紹仍在 Render，因此點入介紹頁仍可能遇到喚醒等待。未加入代理、付費常駐服務、Service Worker 離線資料或第二套資料庫。若未來加入登入、Cookie 或寫入 API，必須重新收緊 CORS，不能沿用 wildcard。
- **驗證**：2026-10-19 正常同源 React build、`/event-radar/` 子路徑與外部 API 設定的 Pages build、TypeScript 型別及 74 項單元測試通過；Pages 產物的 JS／CSS 路徑、canonical、GA4、`noindex` 與 Render API 根網址已核對，28 張公開圖片由 workflow 複製進同一 artifact。第一次 Pages 工作因儲存庫尚未啟用而停在 `configure-pages`；將 Source 設為 GitHub Actions 後，[attempt 2](https://github.com/AndyLinStrongtyping/event-radar/actions/runs/39191373569) 成功。[CI #64](https://github.com/AndyLinStrongtyping/event-radar/actions/runs/39191373507) 以隔離 PostgreSQL 通過新增的 CORS／HTTP 契約。Render 手動部署 `9de79ed` 顯示 Live；公開請求驗證 Pages、主圖、API 均為 200，`Access-Control-Allow-Origin: *`，11 間館所、25 筆未結束特展，health 與 database 皆 `ok`。Chrome 開啟 Pages 後可見介面、圖片與 25 場結果。這是單次發布與瀏覽器驗收，不代表冷啟動已消失、跨日可用性或付費 SLA。

### ER-96｜故宮北院官方清單缺展時保留有效資料，逐筆人工補充（已上線）

- **問題**：2026-10-20 官方當期 JSON 回 22 筆，依既有規則僅 1 筆可公開；館方當期頁另有《真知灼見》與《養心》兩檔展覽，不能把 HTTP 200 視為完整清單，也不應因已知漏展阻止其他合格資料更新。
- **決策**：以 `probe:npm-north` 唯讀比對有時限的已知展覽。官方匯入發現缺漏時仍逐筆匯入合格資料，將涵蓋狀態標為 `deferred_partial`；不建立或更新完整清單基準、不依缺席下架既有展覽，也不推進 `last_official_success_at`。兩檔核對過展名、展期、展廳和館方詳情網址的資料以獨立 `npm-north-manual` 來源補充；人工成功不能冒充官方清單完整。北院雲端週排程維持關閉。
- **驗證與限制**：故宮[官方新聞](https://www.npm.gov.tw/News-Content.aspx?idstr=MDMwMDAwOTY%3D&l=1&sno=04014651&type=03000096)可核對兩檔展訊。乾淨發布分支的 79 項單元測試、型別與文件檢查通過；隔離 PostgreSQL 整合測試確認人工補充首次新增 2 筆、重跑無重複，且不推進官方同步時間。2026-10-21 備份後匯入正式 Neon，官方清單標為 `deferred_partial`；Render 部署成功，公開 API 可讀到兩檔人工補充。這只補兩檔已知漏展，不能保證整份清單完整；尚未證明 GitHub runner 可連官方 JSON。詳見[上線驗證紀錄](stage-2026-10-21-npm-north-release.md)、[來源稽核](stage-2026-10-20-open-data-audit.md)及[維運手冊](operations.md)。

**2026-10-21 第二輪補查 ER-96**：館方當期／預告清單及逐筆詳情另確認〈匯流1950〉、〈物華再現〉、〈獨具慧眼〉、〈國寶聚焦 2026-III〉，可取得的官方 JSON 均未列出。前者展期恰為 730 天，未超過現行兩年上限；其餘三檔有完整限期。保留同一人工來源及原有冪等鍵，補充檔擴為六筆，缺漏探測只在各檔展期內警示。待審的長期／常設展示與外館展不因此自動核准；這仍是已知展的補救，不是完整新展發現機制。驗證及部署狀態見[第二輪稽核](stage-2026-10-21-npm-north-second-audit.md)。

**2026-10-21 展覽來源標籤修正 ER-96**：公開查詢原以館所 `source_status` 標示每筆展覽，使北院人工核對補展被誤稱為 `open_data`。清單及詳情改依展覽 `primary_provider` 對 `npm-north-manual` 回 `curated`，其餘保留館所狀態；整合測試以六筆人工補展驗證兩種端點。館所本身的資料來源與健康狀態仍維持原欄位，不將人工補正冒充官方清單同步。[PR #10](https://github.com/AndyLinStrongtyping/event-radar/pull/10) 合併後，Render 部署 `3db2f41` 上線，公開 API 實查六筆 `curated`、一筆 `open_data`；見[第二輪稽核](stage-2026-10-21-npm-north-second-audit.md)。

## ER-97｜桌面快速跳轉避開特展查詢

- **問題**：公開頁在約 1,265px 寬的桌面視窗中，固定於右側的快速跳轉覆蓋特展查詢面板右端，遮住館所選單與「重新查詢」按鈕。
- **決策**：保留長頁面的快速跳轉。在 1,050～1,799px 寬的桌面視窗縮成右側 40px 圖示列，放在內容的右側留白；每個圖示保留鍵盤可聚焦的連結、中文無障礙名稱與滑鼠提示。1,800px 以上才展開文字版；手機沿用既有不顯示側邊導覽的規則。這樣在特展搜尋與其他區塊都不覆蓋操作區。
- **驗證**：前端型別與建置檢查、公開頁問題畫面及本機修正後的桌面互動檢查。這是版面改善，不改動搜尋 API 或篩選規則。

## ER-98｜修復子路徑導覽並補回人工核對的奇美特展

- **問題**：GitHub Pages 前端的深海區「查看海生館全部展覽」使用網站根路徑，會跳到個人首頁。奇美篩選在正式 API 為 0 筆；唯讀查詢正式庫確認 `exhibitions`、`source_records` 與奇美匯入紀錄都沒有資料，而官網仍列出《埃及之王：法老》。舊的每日節目快照也被文案稱為「今日」。
- **決策**：海生館連結改由 `appUrl` 產生，兼容根目錄及 `/event-radar/` 部署；歷史快照改稱「這次的觀察紀錄」。奇美先以獨立人工核對 JSON 保存一筆展名、完整日期、展廳、票價提示與官方網址，沿用正規化、穩定來源鍵、冪等匯入及異動紀錄；`curated` 不冒充官方自動同步。空搜尋結果明示本站收錄界線，慢速連線超過 8 秒才補提示；免費篩選仍只接受明確標示免費的展覽。
- **界線**：這只修正一筆確定漏掉的奇美特展，不能證明奇美清單完整或來源可穩定自動更新。官方價格與場次仍以館方為準；後續人工重跑須先核對官方詳情頁。資料庫匯入不會改動奇美內部候選 API 的啟用門檻。
- **驗收**：PR #13 的 GitHub 自動檢查通過。公開 Pages 連結點擊後留在 `/event-radar/?museum=nmmba#explore-title`，館別選中海生館、結果顯示 2 場；奇美館別公開頁顯示 1 場《埃及之王：法老》，展期、特展廳、票價及官方詳情連結可展開查看。這是桌面瀏覽器的單次公開回歸，未涵蓋手機實機或跨週來源穩定性。
- **驗證**：乾淨發布分支的前後端型別、80 項單元測試、文件連結及 `/event-radar/` 前端建置通過；正式匯入回報新增 1 筆，公開 `/exhibitions?museum=chimei&status=all` 回 `total=1` 且 `sourceStatus=curated`。前端的公開 Pages 跳轉仍須部署後實測。

## ER-99｜只記錄有意圖的核心操作，週報決定下一項改善

- **問題**：既有 GA4 只確認 `page_view`／`session_start`，無法判斷訪客是否成功搜尋、打開展覽資訊或前往館方；多份現況文件仍把 2026-10-20 週排程寫成未觸發。
- **決策**：React 僅在使用者變更篩選或主動重查，且最新 `/exhibitions` 請求成功後送 `exhibition_search_complete`；初始載入、失敗／被取消的請求、載入更多與測試資料不計。展覽檔案只在關閉轉展開時送 `exhibition_detail_open`，特展卡片「館方原頁」被點擊時送 `official_exhibition_click`。事件參數限結果筆數、固定選項、館所 ID、展覽穩定 ID 與來源狀態；不送使用者輸入的搜尋字詞、展名、日期或外部網址。GA4 未載入或出錯時，網站操作繼續正常進行。首頁連到[網站流量與隱私說明](../web/privacy.html)；週報固定記錄流量、互動、來源健康及維護時間，再選一項改善。
- **驗證與界線**：82 項單元測試及型別檢查通過，新增測試確認事件不含原始搜尋字詞／展名／網址、測試資料不計。第一次[真實週排程](stage-2026-10-21-first-weekly-schedule.md)六個工作成功，北院略過；跨週穩定尚未證明。10/25 [PR #15](https://github.com/AndyLinStrongtyping/event-radar/pull/15) 兩項檢查通過後合併；Pages 第 16 次發布與 Render `3d95936` 手動部署成功。公開站搜尋回 32 場、`/privacy.html` 可開啟；人工重查、展開檔案、點擊館方原頁後，GA4 即時總覽三個新事件各收到 1 次。這是站長測試，不是訪客成效；歷史事件報表及跨週趨勢仍待核對。GA4 自訂參數若要在一般報表分組，仍需後台建立自訂維度。事件計數不是獨立訪客數。[每週紀錄](weekly-product-review.md)分開記已取得與未取得數字。

## ER-100｜首頁保留展覽搜尋，深海與化石改為獨立主題頁

- **問題**：首頁同時放特展、票務、14 篇館所入口、表演、深海與化石完整內容。訪客為了回到搜尋或切換主題要捲過過長頁面；`#deep-sea` 與 `#fossils` 也不能分別分享有獨立標題的頁面。
- **決策**：首頁保留特展搜尋、館所圖鑑、票務、奇美活動與表演節目；三張探索卡、頂部選單及桌面捷徑導向 `/explore/ocean/` 和 `/explore/fossils/`。兩個主題沿用原本的館別切換和內容，不改動匯入資料。Vite 多頁建置、Node 與本機預覽各自提供可直接開啟的 HTML；主題頁各有標題、描述、相互導覽與回頂按鈕。Render 的 sitemap 與 canonical 加入兩個網址，Pages 對應頁維持 `noindex` 並指回 Render。舊首頁深海／化石錨點在 React 啟動前轉往新頁，館所介紹內鏈改指新網址。
- **取捨與驗證**：這次解決內容過長與直接分享入口，不宣稱首頁已縮成單螢幕，也沒有把 React 內容改成伺服器預先產生；搜尋引擎收錄成效仍須 Search Console 後續觀察。本機型別、82 項單元測試、文件檢查及一般／Pages 子路徑多頁建置通過；Chrome 直接開啟兩個主題頁、首頁卡片可導航，化石頁 390px 手機寬度目視沒有橫向溢出。[PR #17](https://github.com/AndyLinStrongtyping/event-radar/pull/17) 與合併後 CI 成功，Pages #18 及 Render `ae0356e` 發布成功；公開 smoke 通過，Pages／Render 新路由、海生館資料和舊錨點轉向均由瀏覽器核對。完整證據見[公開驗收紀錄](stage-2026-10-25-theme-pages-release.md)。手機實機與 10/27 第二次週排程尚待驗收。

## ER-101｜搜尋內容先服務行前決策，再按證據擴館（規劃，尚未實作）

- **問題**：館所攻略可吸引「門票、開館、預約、看什麼」等具體需求，但目前 Search Console 連結報表只有 10/19～10/24 的零曝光基準，沒有實際查詢；新 React 主題頁的文字及 Render 免費主站休眠也須先確認 Google 能讀到。若直接按熱門詞量產故宮、奇美、化石、鐵道、海洋與茶業文章，可能產生重複薄內容和過期票務資訊。
- **規劃取捨**：每組行前決策需求先對應一個主要館所頁，使用既有靜態 HTML 增補可核對的官方票務、導覽、展覽入口和最後核對日期；故宮北／南院、常設／特展、每日節目／歷史快照分開說明。Search Console 原站網址審查與標準網址、Render 可用性、React 頁實際可讀文字是擴張前的技術門檻。首批故宮北院、奇美、左鎮、澎湖；海科館、茶博館、鐵道館先研究來源，不承諾已收錄。餐飲心得需實際走訪才寫，聯盟導購等產品有可信內容與流量後再評估。
- **驗證界線**：[完整計畫](seo-content-plan.md)列出 11 組候選查詢與頁面對應、來源檢查、更新責任及搜尋成效驗收；這是規劃文件，沒有改網站、資料來源、Search Console 設定或廣告。候選字詞未取得搜尋量，沒有排名預測；Google 是否收錄或帶來流量仍待後續實測。

## ER-103｜首頁搜尋文案與實際查詢能力一致

- **問題**：首頁偏重「發掘、線索」的風格用語，第一次到訪不容易辨識展覽查詢入口；建議中的「搜尋展覽、博物館或城市」則超過目前關鍵字查詢能力。
- **決策**：保留考古視覺與展館雷達品牌，主標題改為「探索台灣近期展覽」，導覽使用「找展覽」，同步首頁 title、分享標題及摘要。關鍵字框明示搜尋展覽名稱，城市及館所沿用既有篩選；不改日期狀態、免費認定與 API，不新增未有內容的語言切換或城市頁。
- **實作**：首頁、深海與化石頁在 React 載入前提供真實主題文字及館所連結，載入後仍由既有互動介面接手；故宮北院、奇美、左鎮、澎湖頁使用與內文一致的標題、描述。票價只在官方頁可核對時附日期與來源；不能核對的故宮票種只連官方入口。
- **驗證與界線**：82 項測試、型別、建置及文件檢查通過；Search Console 原站顯示首頁已索引，sitemap 讀取成功，但其他頁仍待 Google 檢索。尚未發布，不代表搜尋排名改善或已完成城市搜尋專頁。見[實作紀錄](stage-2026-10-25-seo-release.md)與[搜尋內容計畫](seo-content-plan.md)。

## 後續更新方式

每次功能或技術決策有變動，**同一個提交**更新對應的 ER 編號：將「規劃」改為實際狀態，寫明實作方法、取捨、失敗情境與可重現的驗證，附程式／測試路徑；若改變資料來源或對外承諾，同步更新 [STATUS](../STATUS.md)、[API 契約](api.md)、[架構](architecture.md)或[運作設計](operations.md)。新增技術點接續編號，不要刪除曾影響設計的決策；被取代的做法標註原因與日期。**只有測試通過或實際連線核對過的項目，才能寫「已驗證」。**
