## 非同步處理的實作順序

1. **先使來源匯入可靠。** 取得科博館 API Key 與正式文件後，確認授權、速率限制、分頁及錯誤格式，將金鑰放在伺服端 Secret，更新 adapter、契約測試與整批失敗判定。Key 是存取憑證，並非 Queue 的必要條件。
2. **來源各自成為工作。** 每日排程分派 `FETCH_SOURCE` 工作，各館獨立逾時、限流、重試與失敗紀錄；一館失敗不阻塞其他館。先做這個情境，再決定使用 PostgreSQL 工作表或 Redis/BullMQ，不為少量每日工作預設新增服務。
3. **拆開資料處理。** `FETCH_SOURCE → PARSE_SOURCE → NORMALIZE → UPSERT → CHECK_CHANGE`。每步使用穩定來源鍵及唯一約束保證重跑冪等；解析失敗保留來源與原因，欄位異動須在資料庫交易完成後才發出後續工作。工作重試須有上限、退避與可人工重跑的失敗佇列。
4. **以量測證明價值。** 測試來源逾時、格式變動、重複派工、部分失敗及大量資料；記錄成功率、耗時、重試次數、來源最後成功時間及異動數。只有資料量或故障模式證明需要時才擴大 worker 數量。

Email／LINE 異動通知需先有訂閱、同意、頻率限制與防重寄設計；圖片下載、縮圖與 WebP 轉換需先確認圖片使用權；第三方地圖、AI 分類、翻譯、夜間統計與 Webhook 目前沒有產品需求或實作，不列入近期里程碑。歌劇院、文化局與市集也不在本輪博物館特展範圍內；若日後擴大，需先重新定義資料類型與搜尋規則。

## 下次資料清洗方向：海生館 JSON

[實際查證](api-source-research.md#公開-json-實際回應抽查2026-10-04)顯示海生館特展 JSON 有民國年數字、ISO 日期及大量缺漏；下一次接來源時採取「原始資料留存 → 解析驗證 → 分流」：

1. **日期解析。** 例如 `1150618` 可按已確認的資料格式解析為民國 115 年 06 月 18 日，再換算為 `2026-06-18`。ISO `YYYY-MM-DD` 也需檢查日曆上確實存在、起日不晚於迄日、展期合理。單看長度或字串含 `-` 不足以判定有效日期；不能讓程式默默將不存在的日期進位。
2. **A：可搜尋特展。** 起訖日期完整且有效、有可追溯的官方資料來源，才進搜尋索引。來源的原始值與正規化值都保留，供日後核對及異動偵測。
3. **B：已確認的常設展或長期展示。** 必須有館方明確標示「常設」或其他可核對的長期展示證據，才可放入獨立導覽。**缺結束日不能自動推斷為常設展或正在展出**；「巨鯨之路」等個案也應先核對館方現況。
4. **C：隔離待審。** 日期缺失、格式不明、官方連結無法核對或分類有歧義者，只存原始內容、來源網址、錯誤原因與發現時間，不進前端搜尋。若內文看似有日期，也先人工核對再建立帶證據與審查紀錄的修正，不能讓解析器猜補。
5. **告警與重跑。** 初次全量資料可能有大量歷史缺漏；通知應按來源、錯誤類型及首次／新變更聚合，避免每次排程重複寄送。增量處理仍須驗證每筆資料，不預設「新資料一定較乾淨」。先建立後台隔離清單與 Email 摘要，後續才評估 LINE Messaging API。

[LINE 官方公告](https://developers.line.biz/en/news/2025/04/01/line-notify/)指出 LINE Notify 已於 2025-03-31 終止，不能列為實作選項；若要 LINE 通知，需另評估 Messaging API 的帳號、費用、收件對象與同意流程。上述 A／C 分流、海生館匯入與本機待審清單已完成；人工修正證據與審查紀錄、告警／通知服務仍待實作。
