# Event Radar｜面試用專案介紹

核對日：2026-10-16。這份介紹只使用目前本機可重現的成果。正式網址、陌生使用者、自然搜尋流量、線上持續更新、AWS 維運及營收都**尚無證據**，不可放進已完成敘述。技術細節與限制分別見[架構](architecture.md)、[ERD](erd.md)、[來源盤點](sources.md)及[Phase 7 驗收](stage-2026-10-16-phase7.md)。

## 30 秒介紹

> 我獨立開發 Event Radar，一個整合博物館限期展、表演場次與海洋節目的本機平台。不同館所的 JSON 和 HTML 先經來源 Adapter 驗證、標準化，再做同來源冪等匯入與欄位異動追蹤；缺日期或來源不明的紀錄隔離待審。後端使用 Node.js、TypeScript 與 PostgreSQL，前端使用 React。現有功能通過單元、隔離資料庫／HTTP 整合及 OpenAPI 回應契約測試。專案尚未公開部署，下一階段是部署與線上穩定性驗證。

## 技術展示順序

1. **用一筆來源異常說明資料品質**：海生館原始資料缺日期、歌劇院場次不等於仍有票；驗證失敗會待審或整批拒收，不在訪客搜尋中猜補。清單筆數或來源鍵大幅改變時保留上次成功資料，站長附官方證據才能放行。
2. **用同一活動重跑說明冪等與異動**：穩定來源鍵加唯一約束防重複；內容 hash 與欄位 diff 分辨「未變」及真正修改，異動歷史留下欄位、前後值與時間。
3. **用三種時間模型說明領域設計**：限期展是日期範圍，表演節目有多個 `EventSession`，海生館節目是某天觀察到的本地時段與完整快照。資料庫複合外鍵避免把表演場次掛到海洋節目。
4. **用測試說明工程邊界**：固定來源樣本驗證解析、無效資料與重跑；隔離 PostgreSQL 及真實 HTTP 回應驗證 migration、匯入與 OpenAPI；不讓 CI 依賴外站即時內容。
5. **展示介面並交代來源等級**：React 的特展搜尋、表演與深海區可用；奇美活動、沖繩與兩座化石館中有人工快照或靜態導覽，畫面會導回官方，不宣稱即時同步。

## 可以量化的現況

截至 Phase 7 本機驗收：**72 項單元測試通過**，TypeScript 型別、React build、隔離 PostgreSQL／HTTP 整合及公開 GET OpenAPI 回應契約通過。歌劇院 `place=1` 官方清單於 2026-10-15 手動同步接受 20 筆、全部未變；海生館 10/12、10/13、10/15 有當日觀察，10/15 的九筆同步全未變。這些是**有日期的本機樣本**，不是持續更新率、全站覆蓋率或線上 SLA。真正的流量、故障率與可用時間要待部署後量測。

## 面試常見追問

**為何不把所有事件放同一張表？** 展覽、表演與每日節目的時間語意不同。強行共用一組可空起迄日期會讓「今天看到的餵食時段」看起來像未來每天有效；目前保留分領域表與分型 API。

**Queue 做到哪裡？** 只有本機 PostgreSQL `FETCH_SOURCE` 工作：同館同日去重、租約、有限重試、dead 與人工 replay。多階段 Parser／Change／Notification worker 和 production 排程尚未完成；不把概念架構圖說成現有系統。

**為何來源消失時不直接刪？** 官網改版、篩選行為或暫時故障都可能讓清單縮水。系統保存成功基準和缺席候選；異常批次保留上次可用資料並要求人工核對。

**目前最大的風險？** 外部來源跨週格式與清單涵蓋率未證明，奇美官網內部端點沒有公開文件化供第三方使用。公開測試版前須收斂可維護的來源範圍，完成遠端環境、Secret、migration、HTTPS、健康檢查與部署後 smoke test。

## 履歷可使用的現階段寫法
