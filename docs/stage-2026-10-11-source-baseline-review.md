# 2026-10-11｜官方清單異常後的人工基準審查

## 問題與決策

來源鍵大幅替換會被完整度閘門暫緩，能避免錯誤下架；正常換季也會觸發相同保護。不能靠再次匯入自動放行，否則解析器錯位造成的假清單也可能變成新基準。本階段加入只有站長可用的命令列核對流程，不對訪客開放寫入 API。

## 實作

- migration 014 新增 `ingestion_runs.source_identity_keys` 與 `source_baseline_reviews`。歷史批次的鍵快照保持空值，僅新的官方匯入可成為核准候選。
- `coverage:baseline inspect` 顯示最新官方匯入與可信基準的來源鍵差異。來源鍵可能來自 HTML 與 JSON 兩路核對，因此來源鍵數不一定等於可公開展覽筆數，必須一起看 `candidateRows`。
- `coverage:baseline accept` 要求最新成功但被暫緩的批次 UUID、該館同網域 HTTPS 官方證據、審查人與說明。資料庫交易和匯入共用館別鎖，再查一次批次與基準，避免審查時被新匯入取代。審查紀錄與基準更新一起提交。
- 核准只更新後續比較基準，既有展覽照常可見，舊批次的歷史狀態不變。下次官方同步若清單仍與新基準一致，才會重新通過 `checked`，並走原有缺席候選流程。

## 驗證與限制

- `npm run typecheck` 通過；`npm test` 43 項通過。
- `npm run test:integration` 以隔離 PostgreSQL schema 通過：同數量全換、差異預覽、錯誤網域及批次拒絕、審查紀錄、重複拒絕、不隱藏舊展、下一次相同清單恢復檢查。
- 本機既有 `event_radar` 資料庫執行 `npm run migrate`，顯示新套用 1 份、共 14 份；未刪除或回填既有展覽。沒有對真實來源執行基準核准，也沒有啟用線上同步。
- 即使提供官方網址，系統無法自行判斷審查人是否真的核對完整清單。來源縮水、分頁、館方改版與展覽取消仍需人工確認；核准不是來源可靠性的自動證明。
